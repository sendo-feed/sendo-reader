# アカウントの画面

- 状態：提案中
- 関連：[ローカルファースト](local-first.md)（6 のログインと「ページの守り」）、[UI とツール](ui.md)、sendo の[ユーザーと認証](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/accounts.md)（7 のアクセストークン）・[MCP サーバー](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/mcp.md)（4〜7 の OAuth と許可の画面）

ブラウザでログインした人（sendo のセッション）だけが使える sendo の API がある。アクセストークンの発行・一覧・取り消し、OAuth で出した許可の一覧・取り消し、OAuth の許可の画面のための API。reader の設定画面では、ログインした利用者が Reeder などのリーダーアプリや MCP クライアント用のトークンを発行・管理できる。

## 決定

1. **設定の画面（`/settings`）で、アクセストークンと OAuth の許可を管理する。**
   - アクセストークン：一覧（名前、用途、範囲、作った時刻、最後に使った時刻）、発行（名前と用途。MCP 用なら範囲を `read` だけか、`read` と `write` から選ぶ）、取り消し
   - OAuth で出した許可：一覧（クライアントの名前、範囲、許可した時刻、最後に使った時刻）、取り消し
   - 取り消すときは、画面の中で確かめてから送る（取り消したトークンや許可は、すぐに使えなくなる）
2. **設定の画面と許可の画面は、ネットワークが要る画面にする**（[ローカルファースト](local-first.md)の 1 の例外）。手元の DB に置かず、開くたびに sendo に聞く。読み込んでいる間はその旨を出し、オフラインや sendo に届かないときは、その旨とやり直す手段を出す。
3. **sendo の API は、core の API の窓口を通して呼ぶ。** タイムアウト、中断、失敗の分け方を、同期と揃える。結果は手元の DB に書かない。
4. **発行したトークンの中身は、一度だけ出す。** 発行の応答で受けた中身を、その画面にだけ出し、コピーのボタンを付ける。画面を離れたら消える。手元の DB、`localStorage`・`sessionStorage`、ログ、エラーの表示、URL、Service Worker のキャッシュには入れない（[ローカルファースト](local-first.md)の「秘密を外に出さない」）。
5. **OAuth の許可の画面（`/oauth/authorize`）を置く**（sendo の [MCP サーバー](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/mcp.md)の 4。手順と API の形は sendo が正）。
   - 開いたら、`location.search` をそのまま sendo に送って確かめ、正しいリクエストなら許可の画面を出す
   - 出すもの
     - クライアントの名前。動的登録のクライアントなら「名乗っただけで、確かめていない」と添える
     - クライアントの ID の URL のホスト（ある場合）
     - 戻る先のホスト（必ず出す）。戻る先が手元（`localhost` など）なら、この端末のほかのアプリも受け取れる旨の注意
     - 求めている範囲（`read` は読むだけ、`write` は購読や既読などの変更も）
     - 許可するアカウント（ログインしているメール）
   - 許可か拒否かは、毎回、利用者が押して決める。自動で許可したり、「次から聞かない」を作ったりしない
   - 選んだ結果を sendo に送り、sendo が返したリダイレクト先へだけ移る。誤りで、リダイレクト先が返ってこなければ、画面に誤りを出し、どこへも移らない
   - ログインしていなければ、クエリをそのタブの `sessionStorage` に置いて、いつものログイン（`returnTo=/oauth/authorize`）に回し、戻ったら置いたクエリで続ける。置いたクエリは、使ったら消す
   - sendo で OAuth を使う設定がなければ、その旨を出す
   - 許可の画面は、sendo のセッションだけで動き、reader の手元のデータ（ログインしたユーザー、同期）を使わない。reader で読んでいない人も来る
6. **クライアントの名前など、sendo が外から受け取った文字列は、信頼できないプレーンテキストとして出す。** `{@html}` を使わず、長すぎれば切って出す（[UI とツール](ui.md)の守る規約）。許可の画面も、ほかのサイトの枠には入れない（CSP の `frame-ancestors 'none'` のまま）。

## 理由

- **ネットワークが要る画面**：トークンと許可は sendo にしかなく、発行も取り消しも sendo に届かなければ意味がない。手元に写した一覧は、別の端末で発行・取り消ししたものとずれ、取り消したはずのトークンが残って見える。許可の画面は、そもそも sendo とその場でやり取りする手順。
- **core の窓口を通す**：届かない、時間切れ、セッション切れの扱いが、同期とほかの画面で揃う。
- **トークンを一度だけ出す**：sendo も中身は発行の応答でしか返さない（DB にはハッシュだけを置く）。手元に置くと、XSS や端末の持ち出しで漏れる場所が増える。控え損ねたら、取り消して発行し直せばよい。
- **毎回、利用者が押して許可する**：同じ sendo にログインしていても、どのエージェントにどこまで許すかは利用者が決める。自動で許可すると、悪いクライアントが利用者に URL を踏ませるだけでトークンを手に入れられる（sendo の mcp.md の理由と同じ）。
- **sendo が返した先へだけ移る**：戻る先が登録と合っているかは sendo が確かめる。画面がクエリの `redirect_uri` を見て移ると、確かめていない先へ認可の結果を渡しうる。
- **クエリを `sessionStorage` に置く**：sendo のログインの `returnTo` は 1024 文字までで、認可のクエリは入りきらないことがある。`sessionStorage` はそのタブの中だけで、ほかのサイトからは読めない。
- **許可の画面で手元のデータを使わない**：Claude.ai などからつなぐ人が、reader で読んでいるとは限らない。許可するだけのために、手元に同期を始めない。

## 検討した代替案

- **トークンと許可の一覧を手元に写し、オフラインでも見られるようにする**：見るだけなら害は小さいが、sendo とずれる。発行と取り消しはオンラインでしかできないので、写す利点が小さい。
- **発行したトークンを手元に置き、あとから見られるようにする**：控え損ねても困らないが、漏れる場所が増える。
- **同じクライアントと同じ範囲なら、次からは自動で許可する**：手間は減るが、上の理由で危ない（sendo の決定でも禁じている）。
- **許可の画面を sendo が出す**：sendo の決定（mcp.md の 4）で reader に置くと決まっている。
- **認可のクエリを `returnTo` に入れてログインに回す**：作りは小さいが、長いクエリで切れる。
- **`/settings` の API を、画面のスレッドから直接 fetch する**：手軽だが、タイムアウトや失敗の分け方が同期と揃わない。

## 見直す条件

- sendo のトークンや許可の API（とくに許可の画面の手順）の形が変わったとき。
- トークンや許可を、オフラインでも見たいという要望が出たとき。
- ネイティブ（Capacitor）で包むとき。許可の画面をアプリの中で出すか、ブラウザに任せるかを決める。
