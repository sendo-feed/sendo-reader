# UI とツール

- 状態：提案中
- 関連：[ローカルファースト](local-first.md)、[記事の翻訳](translation.md)、[コンテナ版](container.md)、[速さの予算](performance.md)、[記事の中の X の投稿](embeds.md)、sendo の[テックスタック](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/tech-stack.md)、[技術構成](https://github.com/sendo-feed/sendo/blob/main/docs/tech-deck.md)（4・7・8 の未決事項 1・6）

## 決定

1. **UI は Svelte 5 ＋ Vite で作る。** SvelteKit は使わず、SPA にする。画面の切り替えは、History API を使う小さな自前のルーターで行う。
   - **読み込み直しても、戻る・進むでも、同じ画面の同じ位置に戻る。** どの画面か（一覧、探す言葉、開いている記事）は URL に、その画面のどこを見ていたか（一覧と記事の位置）は履歴の項目（`history.state`）に持つ。記事の画面では、訳文と原文のどちらを出しているかも、記事の位置と一緒に持つ（[記事の翻訳](translation.md)の 3）。記事の位置には、記事の中の X の投稿の幅と高さも持つ（[記事の中の X の投稿](embeds.md)の 5）
   - 一覧の位置は、見出しのすぐ下の記事で覚える。その記事が一覧から消えていたら（未読だけの一覧で読んだ）、並び順で次の記事から出す。位置に戻すときに飛び越えた記事は、既読にしない
   - 同じ一覧の中で記事を開く・閉じるとき（戻る・進むで開く・閉じるときも含む）は、広い画面では一覧の位置を動かさない（開いた記事の行は見えるところまで動かす）。一覧と記事を並べて出しているので、記事を読みながら動かした一覧を、閉じたときに前の位置へ戻さない。狭い画面では、記事の間は一覧が隠れるので、閉じたら記事を開く前の位置に戻す（6）
   - 一覧の表示の設定（未読だけ）は URL に入れず、一覧ごとの設定として持つ（[設定の同期](settings.md)）。メニューや確かめの窓など、その場かぎりの表示も入れない
2. **Void（Cloudflare）は使わない。**
3. **配布する UI は Web の PWA。** ネイティブ版を配布する場合は、`apps/web` のビルドを Capacitor で包み、`apps/mobile` に置く。
4. **配信は、reader のコンテナのサーバーで行う。** 画面のビルドを返し、sendo のパスを compose の中の sendo に中継する（[コンテナ版](container.md)）。ブラウザからは同じオリジンに見えるので、CORS は要らない。手元では、Vite の dev サーバーが、同じ一覧のパス（[コンテナ版](container.md)の 3）を、WebSocket の Upgrade も含めて、sendo の `pnpm dev`（`http://localhost:8787`）に中継する。
5. **PWA にする。** Service Worker で、アプリの外枠と SQLite の wasm をキャッシュし、ネットワークがなくても起動できるようにする（vite-plugin-pwa）。
   - **新しい版には、利用者が何もしなくても切り替わる。** 画面が前に出たときと、開いたままなら 1 時間ごとに、新しい版があるかを確かめる。新しい版は、裏で取り込んですぐ使い始める
   - 開いている画面は、読み込んだときの版のまま動くので、新しい版に替わったら読み込み直す。読み込み直すのは、画面が裏にある間か、次に前に出たときだけ。読んでいる最中には、読み込み直さない
   - 読み込み直すと消えるものを出している画面（設定の画面の、発行したばかりのアクセストークン。OAuth の許可の画面）では読み込み直さず、ほかの画面に移ってから切り替える
   - 初めて入れたときは、読み込み直さない（版の切り替えではない）
   - 読み込み直すまでの間、古い版のタブと新しい版のタブが同時に開いていることがある。タブどうしのやり取りの版が合わないときの扱いは、[ローカルファースト](local-first.md)の 5
   - reader のコンテナの設定（X の投稿の隔離フレームのオリジン）を変えたときも、新しい版として、同じ時点で切り替わる（[記事の中の X の投稿](embeds.md)の 3）
6. **狭い画面（幅 56rem 以下）では、ページ全体をスクロールする。** 一覧も記事も、入れ物の中ではなくページそのものを動かし、見出しは上に、下のバー（一覧の画面）や記事の操作（記事の画面）は下に貼り付ける。
   - iPhone の「画面のいちばん上を押すと先頭に戻る」を効かせるため。広い画面（3 列）は欄ごとにスクロールする
   - 一覧と記事は同じページを動かすので、一覧の位置は reader が覚えておき、記事から戻ったときに戻す。記事を開いたら、記事の先頭から出す
   - 先頭や末尾での、ブラウザ自身の引っぱり（ゴムのような戻り）は出さない（一覧の先頭で下に引く動きは、更新に使う）
7. **開発ツールは sendo と揃える。** pnpm（ワークスペース）、Biome、Vitest。画面を通したテストは Playwright。ただし TypeScript は 6 系にする（理由は下）。
8. **機能はごちゃごちゃさせない。画面ごとに何を優先するかを決め、常に出す操作を絞る。**
   - **読む画面（記事の一覧、記事の画面）は、没入感を優先する。** 常に出す操作は、読み進めるのに要るものだけにする
     - 記事の一覧の行には、操作のボタンを常には出さない。行ごとの基本の操作（既読・未読、Save）は、スワイプに置いてよい（読む画面だけの例外）。スワイプに置くのは、そこにあると察しがつく基本の操作だけにし、使い方は操作の一覧（`?`）に書く
     - 長押し（右クリック）のメニューは持たない
   - **ほかの画面（購読の管理、設定など）は、分かりやすさを優先する。** 操作は見えるところに出し、キーボードの操作やジェスチャー（スワイプ、長押し）にしかない操作は作らない
   - どの画面でも、次を守る
     - まれに使う操作は、出さないか、見えるところから開ける場所（More actions などのメニュー、Settings）に置く。キーボードの操作は、見えるところでできることを速くする近道として足す
     - メニューには、何をするか（操作）を並べる。同じ操作のやり方の違い（ファイルの形式、送り先、範囲など）は並べず、1 つの操作にまとめて、押したあとに選ばせる（例：Download を押してから、HTML か Markdown を選ぶ）
     - 同じ画面に、同じ操作を 2 か所に出さない
     - 機能を足すときは、どこに出すかを、どれだけよく使うかで決める。迷ったら出さない
   - どの操作を常に出すかは、そのときの機能で変わるので、画面ごとの一覧はここに書かない。足すとき・見直すときに、この原則で決める

### lint と整形

- Biome で、`.svelte` のテンプレートまで lint と整形をする（`html.experimentalFullSupportEnabled`）。Svelte 用のルール（`domains.svelte`）も有効にする。
- 型チェックは、`.ts` は `tsc`、`.svelte` は svelte-check で行う。

### 守る規約

- `packages/core` は、UI のフレームワーク（`svelte`）と `apps/` を import しない。Biome の `noRestrictedImports` で検査する。
- 記事のタイトルや要約はテキストで出す。本文の HTML は `packages/core` で許可したタグと属性だけの木に変換し、`ArticleBody.svelte` が要素を組み立てる（[ローカルファースト](local-first.md)の「記事の本文」）。`{@html}` は Biome の `noSvelteAtHtmlTags` で検査する。
- 記事やフィードの URL は、http ／ https であることを確かめてから `href` に入れる。

## 理由

- **Svelte 5**：コンパイラが画面ごとに必要なコードだけを出すので、JS が小さく、速い（[速さの予算](performance.md)）。ネイティブは Capacitor（WebView）で包むので、React Native とコードを共有する利点はない。
- **SvelteKit を使わない**：サーバー側の仕組み（SSR、API のルート）は sendo がすでに持っている。SPA として書き出すと使わない機能が多く、ランタイムの分だけ JS が増える。画面の数は多くないので、ルーターは自前で足りる。
- **Void を使わない**。画面は Svelte の SPA で足り、サーバーの機能は sendo が持つ。
- **手元でも、本番と同じパスを中継する**：`/api` だけを中継すると、OAuth（`/oauth/token` など）、MCP、Google Reader API のパスは、手元では sendo に届かない。本番と同じ一覧を使えば、手元で動いたものが本番でも同じ道を通る。
- **Capacitor**：Web のビルドをそのまま包めて、画面を作り直さずに済む。バックグラウンドの更新、共有の拡張、APNs など、ネイティブの機能はプラグインで足せる。
- **新しい版に自分で切り替わる**：ホーム画面に置いた PWA には、読み込み直す操作がない。ほかのアプリから戻っても読み込み直さないので、新しい版を確かめる機会がなく、古い版のまま動き続ける。sendo は `docker compose pull` で reader と一緒に新しくなるので、画面だけが古い版のまま、新しい sendo を呼び続けるのも避けたい。読んでいる最中に画面が変わると困るので、切り替えるのは、画面が裏にある間か、戻ってきたときにする。手元の操作は、読み込み直しても手元の DB と操作キューに残り、一覧と記事の位置も履歴の項目に残る（1）。
- **見ていた位置を、URL ではなく履歴の項目に持つ**：ホーム画面の PWA は、新しい版に替わると自分で読み込み直す（5）。そのたびに一覧の先頭に戻ると、読んでいた場所を探し直すことになる。位置は端末の幅や文字の大きさで変わり、共有した相手には意味がないので、URL には入れない。履歴の項目は、読み込み直しても、戻る・進むでも残り、項目ごとに別の位置を持てる。一覧の位置をピクセルではなく記事で覚えるのは、未読だけの一覧では、読み込み直すと読んだ記事が消えて、同じピクセルの位置に別の記事が来るため。
- **狭い画面でページ全体をスクロールする**：iPhone のいちばん上を押すと先頭に戻る動きは、ページそのもののスクロールにしか効かない（入れ物の中のスクロールには効かない）。スマホで読む時間がいちばん長いので、Safari でもホーム画面の PWA でも効く作りにする。広い画面は、一覧と記事を並べて別々に動かしたいので、欄ごとのスクロールにする。
- **機能はごちゃごちゃさせない**：reader は読むための道具で、画面にいちばん長くいるのは記事を読んでいる間。ボタンが並ぶほど、読むことから気が散り、狭い画面では押し間違えも増える。どの操作も「あれば使うかもしれない」と言えるので、足すかどうかで迷うと増える一方になる。一度出した操作は、使っている人がいるかもしれず外しにくいので、出すかどうかは、足すときに決める。
- **画面ごとに優先するものを分ける**：読む画面で求めるのは、読むことに浸れること（没入感）。ほかの画面（購読の管理、設定）は、ときどき開いて用を済ませる画面で、求めるのは、何ができるかがすぐ分かること。同じ物差しで絞ると、読む画面にボタンが残るか、ほかの画面で操作が見つからなくなる。
- **キーボードとジェスチャーだけに置かない**：画面に何も出ていない操作は、できることに気づけない。気づけない操作は、ないのと同じで使われない。キーボードやジェスチャーは、見えるところでできることを、速くするための近道にする。例外は、読む画面の行の基本の操作（既読・未読、Save）をスワイプに置くことだけ（次の項）。
- **読む画面の行の操作は、スワイプに置いてよい**：一覧の行にボタンを並べると、記事の並びを読む邪魔になる。既読・未読と Save は、行を読みながらいちばんよく使う操作で、スワイプで動かせることは、メールなどのアプリで察しがつく。それ以外の操作をスワイプに増やすと、気づかれない操作が増える。
- **長押しのメニューを持たない**：長押しには、押してみるまで何も出ていないので、メニューがあること自体に気づかれない。メニューに入れた操作は、ほかの場所でもできるか、使われないかのどちらかになる。
- **やり方の違いは、押したあとに選ばせる**：形式や送り先ごとに操作を並べると、選べるものが増えるたびにメニューが伸び、何ができるかが見えにくくなる。何をするかを先に選び、やり方はそのあとに選ぶほうが、メニューが短いまま保てる。
- **Biome**：sendo と同じ道具で揃えられる。Biome 2.6.4 で試したところ、テンプレートまで読む設定で、ルーン（`$state`、`$props` など）、`{#each}`、`{#snippet}`、`bind:`、`class:` などを誤検出なく lint・整形でき、`{@html}` も検出できた。分かっている弱点は、`generics="…"` の中に `{` を書くと解析に失敗することと、そこでだけ使う型の import が未使用と出ること。使うときは、型に名前を付けてから使う。
- **TypeScript 6**：svelte-check が TypeScript 5・6 にしか対応しておらず、sendo の TypeScript 7 では `.svelte` の型チェックができない。リポジトリの中で版を分けるとエディタの動きが揃わないので、全体を 6 系にする。

## 検討した代替案

- **React（＋ Void）**：Void のアダプタが使え、人も部品も多い。ただし JS が大きくなり、ネイティブを Capacitor で包むなら React Native との共有の利点もない（技術構成の未決事項 1・6）。
- **SvelteKit の SPA モード**：ファイルでのルーティングやデータの読み込みの仕組みが使えるが、上の理由で見送った。
- **Expo（React Native）**：ネイティブの描画で速いが、画面を Web と別に作ることになる（未決事項 2）。
- **「新しい版があります」と出して、利用者が押して切り替える**：切り替わる時を自分で選べるが、押さない人は古い版のまま残る。表示の場所と、消したあとの扱いも要る。
- **ネイティブ（Capacitor）の殻で、いちばん上を押したことを受け取る**：今の作りのまま効かせられるが、殻を作る仕事（署名、配布）が大きく、Web と PWA では効かないまま残る。殻を作るときには、こちらに寄せてもよい。
- **見ていた位置も URL に入れる**（`?y=1200` など）：URL だけで画面を戻せるが、動かすたびに URL が替わり、共有したリンクで相手の画面まで動いてしまう。
- **一覧の表示の設定（未読だけ）を URL に入れる**：リンクで同じ一覧を渡せるが、一覧ごとの設定を端末の種類ごとに引き継ぐ決まり（[設定の同期](settings.md)）と食い違う。
- **操作をすべて出し、要らないものを Settings で隠せるようにする**：人によって使う操作は違うが、設定の項目が増え、既定の画面はごちゃごちゃしたまま残る。ほとんどの人は既定のまま使う。
- **どの画面も、同じ物差しで絞る**：決まりは 1 つで済むが、上の理由で見送った。
- **まれな操作は、キーボードやジェスチャーだけに置く**：画面はいちばんすっきりするが、できることに気づけず、使われない。
- **一覧の行に、長押しのメニューを開くボタンを出す**：メニューに気づけるようになるが、読む画面の行にボタンが増える。
- **やり方ごとの操作をメニューに並べる**（Download HTML、Download Markdown など）：1 回押すだけで済むが、上の理由で見送った。
- **Vite+（Oxlint・Oxfmt）**。Svelte の検証では、Oxlint 1.90 は `.svelte` の `<script>` の中しか読まず（テンプレートで使う変数が分からず、`{@html}` も検出できない）、Oxfmt 0.75 は `.svelte` を整形しなかった。
- **ESLint ＋ Prettier（eslint-plugin-svelte、prettier-plugin-svelte）**：Svelte への対応はいちばん成熟しているが、道具が 2 つになり、sendo と揃わない。
- **TypeScript 7 と 6 を混ぜる**（`packages/core` は 7、`apps/web` は 6）：core の型チェックは速くなるが、エディタや CI で版が揃わず迷う。

## 見直す条件

- Biome の Svelte 対応（実験的な扱い）で困ったとき。ESLint ＋ Prettier に替えるかを比べる。
- svelte-check（または後継）が TypeScript 7 に対応したとき。sendo と揃える。
- Oxfmt が `.svelte` を整形でき、Oxlint がテンプレートを読めるようになったとき。sendo と一緒に Vite+ に寄せるかを決め直す。
- Capacitor で足りないネイティブの機能が出たとき。
- 画面から外した操作を探す声が続いたとき（その操作はよく使うものだった）。出す場所を決め直す。
- 読む画面で、スワイプの操作に気づかれていないと分かったとき。行の操作の出し方を決め直す。
