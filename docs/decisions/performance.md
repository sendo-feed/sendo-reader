# 速さの予算

- 状態：提案中
- 関連：[UI とツール](ui.md)、[ローカルファースト](local-first.md)、[技術構成](https://github.com/sendo-feed/sendo/blob/main/docs/tech-deck.md)（4. 品質の関所）

最優先は「サクサク動く」こと。体感を「画面が操作できるまで」「記事が出るまで」「操作への反応」に分け、それぞれに上限を決めて CI で守る。数字は最初の目安で、試作して見直す。

## 決定

1. **画面のスレッドの JS は、gzip 後 100KB 以下。** 最初の画面を出すまでに画面のスレッドが読む JS（入口とそこから静的に import するもの。Svelte、画面、core の窓口）を数える。
2. **DB のワーカーの JS と wasm は、合わせて gzip 後 550KB 以下。** SQLite（JS と wasm）、同期エンジン、操作キューを含む。画面のスレッドは止めないが、記事が出るまでの時間に効くので、膨らみを止める。
3. **キャッシュ済みの起動から記事の一覧が出るまで、1 秒以内。** 2 回目以降の起動（Service Worker にキャッシュ済み）で、ページを開いてから最初の記事が画面に出るまでを測る。
4. **操作への反応は 100ms 以内。** 既読、スター、フォルダやフィードの切り替えなど、操作してから画面に反映されるまでを測る。

### 測り方

- 1 と 2 は、ビルドした出力の大きさを CI で数え、超えたら落とす。
- 3 と 4 は Playwright で測り、超えたら落とす。条件は、Chromium、CPU を 4 倍遅くする、手元の DB に記事 1,000 件、ネットワークを切った状態（待っていないことも確かめる）。
- 初回の読み込み（キャッシュなし）は、Lighthouse CI で測って記録する。上限は、試作して数字を見てから決める。

## 理由

- **画面のスレッドの JS**：JS は、ダウンロードのあとに画面のスレッドで解析・コンパイル・実行され、その間は操作に反応できない。中くらいのスマホでは、gzip 後 100KB（展開すると 300〜400KB）でも 100〜200ms ほどかかる。PWA でキャッシュしても、解析とコンパイルは毎回かかる。
- **ワーカーを分けて数える**：SQLite の JS（縮小して gzip 後 約 67KB）と wasm（約 406KB）はワーカーで読むので、画面の操作は止めない。画面のスレッドと同じ 100KB に入れると、画面と同期エンジンに残るのが約 33KB になり、得るものに比べて縛りがきつい。代わりに別の上限で膨らみを止め、記事が出るまでの時間で体感を守る。
- **記事が出るまでの時間**：ローカルファーストの利点は、起動してすぐ手元のデータが出ること。ワーカーの起動、wasm のコンパイル、OPFS を開く時間はここに出るので、大きさではなく時間で守る。
- **100ms**：人が「すぐ反応した」と感じる上限（RAIL モデル）。手元の DB だけで終わる操作なので、守れるはず。
- **CPU を遅くして測る**：CI の機械は手元のスマホより速いので、そのままだと遅さに気づけない。

## 検討した代替案

- **ワーカーの JS も含めて 100KB**：決まりは単純だが、上の理由で縛りがきつい。
- **大きさの上限だけで守る**：測るのは簡単だが、wasm のコンパイルや DB を開く時間など、体感に効く部分を見落とす。
- **数字を決めずに測るだけにする**：試作の自由は大きいが、少しずつ膨らんでも止まらない。

## 見直す条件

- 試作して、数字が体感と合わない（守っていても遅い、または厳しすぎる）と分かったとき。
- Capacitor で包むとき。ネイティブで測る条件を足す。
- 本文の表示や検索など、ワーカーに大きな依存を足す必要が出たとき。
