# ローカルファースト

- 状態：提案中
- 関連：[UI とツール](ui.md)、[記事の翻訳](translation.md)、[コンテナ版](container.md)、[アカウントの画面](account.md)、[画像](images.md)、[記事の中の X の投稿](embeds.md)、sendo の[差分同期](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/sync.md)・[ユーザーと認証](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/accounts.md)・[古い記事の片付け](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/retention.md)、[技術構成](https://github.com/sendo-feed/sendo/blob/main/docs/tech-deck.md)（方針 03・06）

## 決定

1. **ローカルファーストで動く。** 画面はネットワークを待たない。読み書きは手元の SQLite に対して行い、sendo とは同期で揃える。例外は、sendo にしかないものを扱うアカウントの画面（トークンと許可の管理、OAuth の許可の画面）で、[アカウントの画面](account.md)で決める。記事の翻訳を頼む操作も、sendo が訳すので、sendo に届かないとできない（[記事の翻訳](translation.md)の 6）。
2. **同期とローカル DB のロジックは、すべて `packages/core` に置く。** core は UI のフレームワークにも `apps/` にも依存しない。SQLite には core の DB の窓口（インターフェース）越しに触れ、Web の実装（下の Wasm）と、ネイティブの実装（Capacitor で包むとき）を差し替えられるようにする。スキーマとマイグレーションは SQL で書き、どのプラットフォームでも同じにする。
3. **同期は sendo の[差分同期](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/sync.md)に従う。** 決まりはそちらが正で、ここには書き写さない。reader の側では、特に次を守る。
   - カーソルの中身は解釈せず、受け取ったものをそのまま送り返す
   - 差分は `GET /api/v1/sync` の 1 回のリクエスト（続きがあれば続けて）で取る
   - 消した印（フォルダ、購読）や消した記録（記事）を受けたら、その行を手元から消す。ほかの表の変化からは消さない。購読をやめた知らせを見て、そのフィードの記事を消さない（受信箱から消えた記事は、記事ごとの消した記録で届く。表ごとにページを送るので、表をまたいだ順序は保証されない）
   - 手元に置くのは、最初の同期で届く範囲（未読、スター、直近 30 日）と、その後の差分
   - reader は記事の古さだけで手元から削除しない。sendo の[保存容量と古い記事の片付け](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/retention.md)などで受信箱から消えた記事は、消した記録が届いたときに手元から消す
   - 最初の同期範囲に入らない、既読でスターのない記事は手元に届かない。記事の一覧は手元の DB を読むため、その範囲の記事が sendo に残っていても一覧には出ない
   - 操作（既読、スター、購読、フォルダなど）は手元にすぐ反映して操作キューに積み、通常の REST API で送る。同期で届いた行には、まだ送り終えていない操作を重ねて画面に出す。ぶつかったら、サーバーが後から受けたほうを採る
   - 「すべて既読」の境界は、同期済みの範囲（カーソル）にする。手元に届いていない記事を、見ないまま既読にしない
   - **sendo の通知（WebSocket の `/api/v1/sync/updates`）を受けたら、すぐ同期する。** 知らせが届く時と、閉じるコードごとの動きは、sendo の[差分同期](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/sync.md)の 9 と、OpenAPI の `/sync/updates` の説明に従う。reader の側では、次を守る
     - つなぐのは代表のタブのワーカーだけにする（ブラウザごとに 1 本）。ログインしている間だけつなぎ、ログアウトしたときと、同期が 401 を返したときは閉じる。ログインし直したら、またつなぐ
     - つないでみて、つながらなければ、間を延ばしながらつなぎ直し、そのあいだも定期同期を続ける。sendo が通知に対応しているかを、別の API で問い合わせない
     - 接続が開いたときと、知らせを受けたときは、少し（0.3 秒）待ってから同期する。続けて届いた知らせや、自分の書き込みのあとの同期とまとめる。sendo が利用者ごとに 1 秒まとめて送るので、reader では長く待たない
     - 自分が送った変更の知らせも届く。同期の差分が空でも何もしない（変わった表がなければ、画面は読み直さない）
     - 通知がつながっていても、起動したとき、オンラインに戻ったとき、前に出たとき、一定の間隔（5 分）の同期は続ける。知らせは欠けることがあるため
4. **Web の SQLite は、公式の `@sqlite.org/sqlite-wasm` と `opfs-sahpool` の VFS にする。** 専用のワーカー（Dedicated Worker）の中で動かし、データは OPFS に置く。COOP ／ COEP のヘッダーは要らないので付けない。
5. **どのタブでも使えるようにする。** タブごとにワーカーを持ち、Web Locks で代表のタブを 1 つ決める。
   - 代表のタブのワーカーだけが DB を開き、同期と操作キューの送信を回す
   - ほかのタブのワーカーは、読み書きを BroadcastChannel で代表に頼む（SQLite の wasm は読み込まない）
   - 代表が書き込んだら、変わった表をすべてのタブに知らせ、各タブは画面に出している読み出しをやり直す
   - 代表のタブが閉じたら、待っていたタブが代表を引き継ぎ、DB を開き直す。引き継ぎの間に頼んだ読み書きは、新しい代表にやり直す（操作は冪等にしておく）
   - 版の違うタブが混ざることがある（新しい版は、開いている画面があってもすぐ使い始め、古い版のタブは読み込み直すまで残る。[UI とツール](ui.md)の 5）。タブのワーカーどうしのやり取りに、版の番号を付ける。番号は、頼める処理や引数の形を変えたときだけ上げる。ふつうの配備では変わらないので、版の混ざったタブもそのまま使える
   - 代表は、自分の番号を名乗る。番号の違う頼みは処理せず、「版が合わない」失敗を返す。番号を名乗らない代表（この決まりより前の版）は、番号が合わないとみなす。代表の番号が合わない間、タブは代表に頼まず、すぐ同じ失敗を返す。黙って待たせない
   - 画面は、その失敗を受けたら、版の違うタブが開いていること、ほかのタブを読み込み直すか閉じれば使えることを知らせる。代表が替わって番号が合えば、そのまま使える
6. **ログインは sendo のセッションで行い、reader はトークンを持たない**（sendo の[ユーザーと認証](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/accounts.md)の 6）。
   - ログインの画面から `/api/v1/auth/google/login?returnTo=<戻るパス>` へページごと移る（fetch ではなく）。Google でログインすると、sendo がセッションのクッキー（HttpOnly）を置いて戻す。失敗したら `/?login_error=<理由>` に戻るので、理由を分かる言葉で出す
   - `/api/v1/auth/...` へのページの移動は、Service Worker で横取りせず、reader のコンテナのサーバー（[コンテナ版](container.md)）の中継で sendo に届ける
   - どのリクエストにも `Authorization` を付けない（付けると、sendo はクッキーを見ない）。前の版が手元に置いたトークンは消す
   - ログインしているかは `GET /api/v1/me` で確かめ、ログインしたユーザー（ID とメール）を手元の DB に置く。起動したら、置いたユーザーで画面を出す（オフラインでも読み書きできる）。手元にユーザーがなければ `/me` を見て、ログインしていればそのまま使い始める
   - 同期と、通信が要る操作の前に、`/me` のユーザーが手元のユーザーと同じかを確かめる。違えば（別のタブなどで、別のユーザーでログインした）、手元の DB を消して最初から同期する
   - `/me` や同期が 401 を返したら（セッションが切れた、取り消された）、手元のデータとまだ送っていない操作は残したまま、ログインし直すよう促す。同じユーザーでログインし直したら、続きから同期する。届かない（オフライン）ときは促さず、手元で動き続ける
   - ログアウトは、`POST /api/v1/auth/logout` を送り、手元の DB をまとめて消す。sendo に届かなくても、手元は消す。そのときは、ログインの操作をするまで、残ったクッキーで自動ではログインせず、届くようになったらログアウトを送り直す
   - 状態を変えるリクエストは、同じオリジンから送る（sendo は、クッキーで認証した状態を変えるリクエストを、`Sec-Fetch-Site: same-origin` のものだけ受ける）。reader のコンテナのサーバーの中継（手元では Vite の dev サーバーの中継）を通るので、そうなる

### 記事の本文

- 記事の本文は、sendo の[記事の本文](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/content.md)に従い、記事ごとに取得する。フィード本文とページから抽出した全文を手元の別々の表に置き、記事を削除したときに一緒に消す。
- 記事を開いたら手元の本文を読み、取得済みの全文はオフラインでも表示する。手元に全文がなければ、フィード本文か要約を出し（フィード本文が手元になければ、取得中は要約を出す）、そのあとに開いている記事の全文を取得する（sendo は全文の抽出を常に動かすので、使えるかどうかは確かめない。[コンテナ版](container.md)の 8）。全文取得に失敗したときも、表示中の本文か要約を残す。訳文のある記事（本文を訳さなかった記事を除く）は、全文ではなく訳した本文を取り、全文は原文に切り替えたときに取る（[記事の翻訳](translation.md)の 3、9）。
- **未読の記事の全文を、これから読む順に先に取っておく。** 開いたときに全文を待たせず、オフラインでも読めるようにする。
  - 同期を終えたあとに、裏で、未読の記事の全文を 1 件ずつ取る。1 回の同期のあとに頼むのは決まった件数までにし（頼んだ数で数え、途中の同期で届いた記事もその中に入る）、続きは次の同期のあとに取る。全文をまだ抜いていない記事は、sendo がそのリクエストの中で元のサイトに取りにいく（sendo の[記事の本文](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/content.md)の 10・17）ので、まとめて一度に頼まない
  - 1 件取るたびに、手元から次の 1 件を選び直す（最初に選んだ一覧を上から取らない）。既読になった記事は選ばれず、途中の同期で届いた記事も同じ回に入る。既読は、この端末なら操作したとき、ほかの端末なら同期で届いたときに、手元に入る。その回で取れなかった記事は、その回では選び直さない
  - 先に取る記事は、未読で、手元に全文がなく、全文が取れなかった印のない記事（印があっても、代わりにフィード本文を取る記事を含む）。選ぶ順は、利用者がこれから読む順に合わせる
    - 画面は、いま開いている一覧（All・フォルダ・フィード・Saved・Search・Recently Read）を core に知らせる。一覧は範囲（All、フォルダ、フィード、Saved はスター付きの記事、Search は探す言葉）で決め、未読だけの絞り込みにはよらない。Saved の保存ページは対象にしない。言葉が空の Search は、一覧を開いていないときと同じにする
    - core はメモリーにだけ覚える（手元の DB にも sendo にも置かない。ログアウトとユーザーの切り替えで消す）。タブが複数あるときは、最後に一覧を開いた・切り替えた・前に出たタブの一覧に従う。代表のタブが替わったときは、次にどれかのタブが知らせるまで、一覧を開いていないときと同じにする
    - 開いている一覧に先に取る記事が残っている間は、その一覧から選ぶ。一覧の中では、その一覧を開いた（画面が知らせた）あとに既読になった記事のうち、既読の時刻が一番新しいもの（同じ時刻なら、一覧の並びで一番下のもの）を目印にし、一覧の並び（公開の新しい順、同じなら ID）で目印より下にある先に取る記事のうち、一番上のものを取る。目印がない（開いてからまだ読んでいない）、または目印より下に先に取る記事がなければ、その一覧の先に取る記事で一番上のものを取る
    - 一覧を取り終えたあと、一覧を開いていないとき、未読のない一覧（Recently Read）を開いているときは、すべての先に取る記事から新しい順に取る
  - 訳文のある記事は、全文の代わりに訳した本文を取る。手元に今の訳した本文がなければ、全文があっても選ぶ。決まりは[記事の翻訳](translation.md)の 10
  - フィード本文は、先に取らない。全文が取れなかった（`page_content_unavailable`）記事で、フィード本文がある（`hasContent`）ときだけ、代わりにフィード本文を取っておく
  - 全文が取れなかった記事は、手元に印を置き、先に取るときには取り直さない。開いたときは、これまでどおり取りにいく
  - 本文の中の画像は、先に取らない（[画像](images.md)の 8。見えた分だけ取る）
- **手元に置く本文の量には、端末ごとに上限を置く。** 全文、フィード本文、訳した本文（[記事の翻訳](translation.md)の 8）の合計で数える。
  - 上限は、設定で選ぶ（Off、50MB、100MB、200MB、500MB、1GB）。既定は 200MB。端末の空きは同じ種類の端末でも違うので、sendo に預けず、その端末だけの設定にする（[設定の同期](settings.md)の 4）
  - Off なら、先に取らない。開いたときの取得はこれまでどおり
  - 上限を超えたら、既読でスターのない記事の本文から、読んだのが古い順に消す。それでも空かなければ、先に取るのをやめる。未読とスターの記事の本文と、最後に開いた記事（いま開いている記事）の本文は、上限のためには消さない
  - 記事を開いたときに取った本文は、上限を超えていても置き、そのあとで既読の分から消す。いま開いている記事の本文は、本文を置いたとき、先に取る前、上限を変えたときのどれでも消えない
  - 最後に開いた記事は、画面が記事を開いたことを知らせ、開封の記録を積むときに、手元に覚える（sendo には預けない。ログアウトで消す）。既読かどうかや、読んだ時刻にはよらない
  - 本文を消しても、記事は消さない（記事は sendo の削除記録に従う。決定の 3）。消した本文は、開いたときに取り直す

### 保存と開封履歴

- 購読外の URL は[あとで読むページ](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/saved.md)として手元に保存し、操作キューと差分同期を使って端末間で揃える。Saved にはスター付きの記事と保存ページを出し、URL が重なったときは記事を表示する。
- 記事を表示したときは、[記事を開いた履歴](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/activity.md)のイベントを操作キューに積む。開封履歴は既読状態と独立して送り、Recently Read の一覧は手元の既読時刻を使う。

### ページの守り

セッションのクッキーは HttpOnly なので、ページの JS からは読めない。それでも、XSS などでページに他人の JS が入ると、ページを開いている間はセッションで API を使われ（クッキーは同じオリジンへのリクエストに付く）、手元の記事や購読のデータも読まれる。そこで、次の対策を取る。

- **CSP を厳しくする。** 本番（reader のコンテナのサーバー）と、手元の Vite の dev サーバー・preview で、画面のすべての応答に付ける。
  - `default-src 'none'`、`script-src 'self' 'wasm-unsafe-eval'`（wasm のため）、`worker-src 'self'`、`connect-src 'self'`、`img-src 'self' data:`、`style-src 'self'`、`manifest-src 'self'`、`base-uri 'none'`、`form-action 'none'`、`frame-ancestors 'none'`、`object-src 'none'`。X の投稿の隔離フレームのオリジンが設定してあるときだけ、`frame-src <隔離フレームのオリジン>` を足す
  - インラインのスクリプトと `eval` を許さない。ほかのオリジンへの通信を許さないので、手元のデータを `fetch` で外に送れない
  - 例外は、X の投稿の隔離フレームのオリジン 1 つだけを、`frame-src` で iframe に許すこと（[記事の中の X の投稿](embeds.md)）。X のスクリプトは隔離フレームの中で動き、reader のオリジンでは動かない。隔離フレームに渡すのは、投稿の ID とテーマだけにする
  - 通知の WebSocket は、同じオリジンの `wss:`（手元は `ws:`）につなぐ。CSP Level 3 では、`connect-src 'self'` が同じホストとポートの `ws:` ／ `wss:` も許すので、CSP は緩めない。本番の CSP のまま、Playwright（Chromium）でつながることを確かめる。`'self'` を `wss:` に当てないブラウザでは接続が止められ、定期同期だけで動く
  - 記事のサムネイルやフィードのアイコンのために、`img-src` は緩めない。画像は sendo が中継し、同じオリジン（`/api/v1/images`）から読む（[画像](images.md)）
  - ほかに緩める必要が出たら、そのときに範囲を決めてこのファイルを直す
  - 手元の dev サーバーだけは、2 つ緩める。Vite が開発中の CSS を `<style>` で差し込むので `style-src` に `'unsafe-inline'` を足し、Vite のエラーの表示が `innerHTML` を使うので Trusted Types を強制しない。それ以外（ほかのオリジンへの通信、インラインのスクリプト、`eval` を許さない）は本番と同じにする。本番と同じヘッダーは、本番のビルドを `vite preview` と Playwright で開いて確かめる
- **Trusted Types を強制する**（`require-trusted-types-for 'script'`）。許すポリシーは、Svelte が作るもの（`svelte-trusted-html`）と、ワーカーの URL を自分のオリジンに限るものだけにする。対応していないブラウザでは効かないので、ほかの対策と重ねる。
- **記事のデータを HTML として出さない。** `{@html}` を使わず、URL は http ／ https を確かめてから `href` に入れる（[UI とツール](ui.md)の守る規約）。
- **秘密を外に出さない。** sendo が返す秘密（発行したアクセストークンなど）は、画面に一度出すだけにし、手元の DB、ログ、エラーの表示、URL、Service Worker のキャッシュに入れない。画像の URL に付く署名は、sendo が配信用に署名した URL であることを示す。画像の取得にはセッションが要る。
- **ログアウトで消す。** ログアウトしたら、手元の DB と、画像のキャッシュ（[画像](images.md)の 4）をまとめて消す（決定の 6）。ユーザーが替わって手元の DB を消すときも、同じく消す。

## 理由

- **ローカルファースト**：最優先は「サクサク動く」こと。画面の操作が手元の DB だけで終われば、通信の遅さや切断に左右されない。iOS ではバックグラウンドで同期できないので、起動したときの同期の速さが体感を決める（技術構成）。
- **core に閉じ込める**：Capacitor で包むときや、UI を替えるときに、同期とデータの作りをそのまま使える。テストも画面なしで書ける。
- **公式の sqlite-wasm**：SQLite の開発元が保守していて、SQLite の版と一緒に出る。Node でもそのまま動くので、core のテストに本番と同じエンジンを使える。
- **opfs-sahpool**：OPFS の VFS の中でいちばん速く、COOP ／ COEP が要らない。COEP を付けると、ほかのオリジンの画像（記事の画像、フィードのアイコン）は、相手が CORP のヘッダーを返さない限り読めなくなる。`credentialless` なら避けられるが、Safari が対応していない。
- **代表のタブ**：opfs-sahpool で同じ DB を開けるのは同時に 1 か所だけ。同期と操作キューの送信も 1 か所で回さないと、同じ操作を二重に送る。ワーカーごと引き継げば、どのタブが閉じても使い続けられる。
- **やり取りの版の番号**：代表が知らない頼みを黙って捨てると、頼んだタブは答えを待ったまま止まる（画面の呼び出しに時間切れはない）。引数の形を変えた頼みは、黙って誤った動きになりうる。番号を、頼める処理や引数の形を変えたときだけ上げれば、ふつうの配備では、版の混ざったタブも今までどおり使える。すでに配った版の代表は変えられないので、番号を名乗らない代表は合わないとみなし、頼む側で止める。
- **セッションのクッキー**：sendo の決定で、ブラウザはセッションを使う。HttpOnly なので、XSS があっても、ログインの秘密そのものは盗まれず、ページを閉じれば使われなくなる。トークンを発行して貼る手間もなくなる。
- **手元にユーザーを置く**：クッキーは JS から読めない。ログインしているかを起動のたびに sendo に聞くと、オフラインで開けない。
- **送る前にユーザーを確かめる**：クッキーは、どのタブのログインでも入れ替わる。手元のユーザーのまま別のユーザーのセッションで送ると、前のユーザーの操作を別のユーザーに書き込み、別のユーザーの記事を前のユーザーの手元に混ぜる。
- **記事は sendo の削除記録に従う**。reader が独自の期限で記事を消すと、同期で受け取った記事を端末だけで失い、一覧を読むために通信が必要になる。保持できる量と端末ごとに届く範囲は、sendo の容量による片付けと最初の同期範囲で決まる。
- **最初の同期の範囲は広げない**：新しい端末で欠けないように、最初の同期で受信箱をすべて送ることもできる。しかし 読まない既読記事の分まで、初回に受け取るデータとリクエストが増える。起動したときの同期の速さを優先する sendo の[差分同期](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/sync.md)の決定にも逆らう。欠けるのは、最初の同期の 30 日より前に入り、読み終えていた記事だけで、片付けの期間がたてば sendo からも消える。
- **通知を受けたら同期する**
  - 開いたままの画面に、取得のジョブが配った新着や、別の端末での既読・購読の変更が、定期同期を待たずに出る
  - 通知は「同期してほしい」の合図だけで、中身を運ばない。差分は今までどおりカーソルで取るので、知らせが重なっても欠けても、手元はずれない
  - 代表のワーカーだけがつなぐのは、同期を回すのが代表だけだから。タブごとにつなぐと、sendo の利用者ごとの接続の上限（8）にすぐ届く
  - つないで判定するのは、sendo の決定と同じ理由。sendo と reader は compose で一緒に更新するので、新旧が混ざるのは短い間だけで、そのあいだは定期同期で足りる
- **全文を先に取り、フィード本文は先に取らない**
  - 記事を開いて読むのは、ほとんど全文。開いてから取りにいくと、記事を開くたびに「全文を取得しています…」が出て、全文に替わるときに本文が入れ替わる。オフラインでは、開いたことのない記事の全文を読めない
  - フィード本文は、全文が出るまでのつなぎで、ほとんど読まない。先に取っても、手元の容量と sendo へのリクエストを使うだけになる。全文が取れない記事でだけ、読む本文になるので、そのときだけ取っておく
  - sendo は取り込んだときに全文を抜いて保存するので、先に取るリクエストの多くは sendo の DB を読むだけで済む。まだ抜いていない記事は sendo が元のサイトに取りにいき、同じサイトには 1 秒空けて順に取る。1 件ずつ、1 回の同期のあとに決まった件数までにすれば、sendo と元のサイトに一度に負荷をかけない
  - 取れなかった記事を毎回頼むと、同期のたびに同じ記事で sendo が元のサイトに取りにいく
- **1 件ごとに選び直し、読む順に合わせる**
  - 先に取るのは、これから読む記事を、開いたときに待たせないため。最初に選んだ一覧を上から取ると、取っている間に読んだ記事（ほかの端末で読んだものを含む）の全文まで取り、途中で届いた記事は次の回まで取らない。選び直せば、どちらも手元の DB の今の状態から決まり、選んだ一覧を書き換える仕組みが要らない
  - 一覧は新しい順で、利用者は上から下へ（新しいほうから古いほうへ）読む。一覧を読み込み直していない間に届いた新しい記事は、いま読んでいる位置より上にあり、すぐには読まない。一覧を開いたあとに最後に既読にした記事は、開いた記事も、一覧を動かして通り過ぎた記事も既読になるので、ふつうはいま読んでいるあたりに当たる。その下の未読から取れば、次に読む記事が先に手元に入る
  - 一覧を開き直すと、上に届いた新しい記事も見え、利用者は上から読み始める。開く前の既読（前に読んで止めた位置）を目印にすると、これから読む上の記事より、止めた位置より下の記事を先に取ってしまう。開いてからまだ読んでいない間は、一覧の上から取る
  - 既読の時刻は、一覧を動かして通り過ぎた記事や「すべて既読」でそろい、sendo が付けた時刻でもそろう。同じ時刻なら一覧の並びで一番下を目印にすれば、通り過ぎた記事のすぐ下から取れる
  - 開いていない一覧の記事は、いま読んでいる一覧を読み終えるまで読まない。開いている一覧を先にすれば、限られた件数と容量を、次に読む記事に使える
  - 開いている一覧は、ログインし直したり、タブを開き直したり、前に出したりすれば、画面が知らせ直す。手元に置いても、次に開いたときには替わっているので、メモリーで足りる。タブを切り替えて読むときは、前に出たタブの一覧を読んでいるので、それに従う
  - 取れなかった記事をその回で選び直すと、選び直すたびに同じ記事が一番上に来て、続けて頼み直すことになる
- **上限を容量で決め、端末ごとに選ばせる**
  - 全文の大きさは記事によって数 KB から数百 KB まで違う。件数で決めると、使う容量が記事次第になる（[画像](images.md)のキャッシュと同じ考え）
  - 置ける量は端末の空き次第で、同じスマホでも違う。決めた値で全員に合わせられないので、選べるようにする。200MB なら、全文が 1 件 50KB として 4,000 件ほど置ける
  - 未読とスターの記事は、これから読む、または残したい記事なので、上限のためには消さない。既読の記事は、読み返すことが少ない
  - いま開いている記事の本文は、消すとオフラインで開き直せず、書き出せない。開くと既読になり、すぐあとに同期と先読みが走るので、既読の分として消すと、開くたびに消えうる
  - 開いている記事は、開封の記録（画面が記事を開くたびに core に知らせる）で分かる。最後に読んだ記事で代えると、既読の記事を開き直したとき（読んだ時刻が変わらない）、開いたまま「すべて既読」や一覧を動かして既読にしたとき、sendo が付けた既読の時刻が同じになったとき、別の端末で後から読んだとき、のどれでも、開いている記事から外れる
- **401 で手元を消さない**：セッションは、30 日使わないと切れ、取り消されることもある。消すと、まだ送っていない操作が失われる。端末を人に渡すときは、ログアウトで消せる。

## 検討した代替案

- **wa-sqlite（`@journeyapps/wa-sqlite`）と OPFSCoopSyncVFS**：複数のタブから同時に DB を開け、JS も小さい（gzip 後 約 31KB、公式は約 67KB）。ただし本家は npm に 2024 年 1 月から出ておらず、使えるのは PowerSync 社の fork で、wasm に使わない PowerSync の拡張が入っていて大きい（約 518KB、公式は約 406KB）。同期を 1 か所で回すための代表のタブは、どちらにしても要る。
- **公式の `opfs` の VFS**：複数のつなぎを持てるが、SharedArrayBuffer のために COOP ／ COEP が要る（上の画像の問題）。
- **SQLite を使わず IndexedDB に置く**：wasm が要らず軽いが、ネイティブと同じスキーマにできず、未読の数や絞り込みのクエリを自前で書くことになる。
- **SharedWorker で DB を持つ**：タブの間の受け渡しが要らないが、OPFS の同期アクセス（`createSyncAccessHandle`）は Dedicated Worker でしか使えない。
- **ビルドの版（コミット）で見分ける**：番号の上げ忘れがないが、配備のたびに、古いタブが読み込み直すまで、版の違うタブが使えなくなる。
- **代表の版が合わない間は、代表が替わるまで待たせる**：失敗を出さずに済むが、古い版のタブを並べて開いたままにしていると、そのあいだ止まり、何が起きているかも分からない。
- **使えるのは 1 つのタブだけにする**：作りは小さいが、2 つめのタブで読めないのは不便なので、最初からどのタブでも使えるようにした。
- **開発のときだけ、トークンを貼る形を残す**：Google の設定なしで試せるが、sendo は Google の設定がないとデプロイできない。手元の確認は、偽の sendo か、手元の sendo の DB に作ったセッションでできる。ログインの道が 2 つになり、トークンを手元に置く危険も残る。
- **通知の接続を、タブごとに持つ**：代表を引き継ぐ手間がないが、タブの数だけ接続が増え、同期を回さないタブが知らせを受けても、代表に頼み直すだけになる。
- **定期同期の間隔を短くする（通知を使わない）**：作りは小さいが、何も変わっていないときも sendo に問い合わせ続け、それでも間隔の分だけ遅れる。
- **起動のたびに `/me` を待ってから画面を出す**：手元にユーザーを置かずに済むが、オフラインで開けない。
- **送る前にユーザーを確かめない（401 だけを見る）**：リクエストが 1 つ減るが、別のユーザーのセッションとの取り違えを防げない。
- **401 を受けたら、手元をすぐ消す**：ほかの人に見られる時間は短くなるが、まだ送っていない操作が失われる。
- **手元では 30 日たった既読の記事を消し、それより古い記事は sendo の一覧（`GET /articles`）から読む**（前の決定）：手元は小さく保てるが、ネットワークを待つ一覧が要る。sendo の一覧は公開日時の順で、手元の範囲は受信箱に入った時刻で決まるので、手元の一覧の続きとしては読めず（手元にある何年も前の未読の記事より新しい、手元にない記事を取りこぼす）、sendo の一覧を最初から読み直すことになる。
- **最初の同期で、受信箱をすべて送ってもらう**（sendo の差分同期を変える）：新しい端末でも初めから揃うが、最初の同期が 3 倍になる（理由を参照）。
- **全文を、開いてから取る**（前の決定）：手元の容量と sendo へのリクエストは少ないが、開くたびに全文を待ち、オフラインでは読めない。
- **フィード本文も全文も、先に取る**：全文が取れない記事でもすぐ読めるが、ほとんど読まないフィード本文のために、容量とリクエストが倍になる。
- **本文の中の画像も、先に取る**：オフラインでも画像まで出るが、画像は 1 枚で数百 KB〜数 MB あり、読まない記事の画像で容量を使う。画像のキャッシュ（[画像](images.md)の 3）とは別に上限を持つことにもなる。
- **最後に読んだ記事で代える**（前の決定）：覚えるものが要らないが、上の理由のとおり、開き直し、まとめて既読、同じ既読の時刻、別の端末での既読で、開いている記事から外れる。
- **開いて取った本文だけを、置いたときに守る**：開いた記事を覚えなくてよいが、開いた直後の先読みの空き作りや、遅れて届いた前の記事の全文を置いたときの消す処理で、いま開いている記事の本文が消える。
- **画面から「いま開いている記事」を、閉じたことも含めて core に渡す**：開いている間だけ正確に守れるが、窓口が増え、タブが複数あるとどれを守るか決めにくい。開封の記録で最後に開いた 1 件を覚えれば、窓口を増やさずに、ふつうの使い方には足りる。
- **最初に選んだ一覧を、上から取る**（前の決定）：作りが小さいが、取っている間に読んだ記事の全文まで取り、途中で届いた記事を次の回まで取らない。
- **一覧は選んだまま、取る直前に未読かだけを確かめる**：既読になった記事は外せるが、途中で届いた記事を同じ回に入れられない。
- **取っている最中の要求も、既読になったら取りやめる**：無駄は一番少ないが、取りやめる仕組みが要り、減るのは多くても 1 件分。
- **すべての未読を、新しい順だけで取る**：開いている一覧を知らなくてよいが、読み込み直していない一覧の上に届いた記事や、開いていない一覧の記事を先に取り、これから読む記事が後回しになる。
- **読んでいる位置を、一覧の表示位置から取る**：既読にしない読み方でも位置が分かるが、画面のスクロールの位置を core に送り続けることになる。開いたあとに最後に既読にした記事で、ふつうの読み方には足りる。
- **目印を、開く前の既読も含めて決める**：一覧を開くたびに数え直さなくてよいが、前に読んで止めた位置より下の記事を、これから上から読む新しい記事より先に取る。
- **上限を件数で決める**：数えるのは易しいが、使う容量が全文の大きさ次第になる。
- **上限を `navigator.storage` の空きから自動で決める**：選ばせる手間はないが、ブラウザが返す値は端末の空きと一致せず、ほかのアプリのための空きまで使ってしまう。
- **モバイル回線では先に取らない**：通信量を抑えられるが、Safari では回線の種類を確かめられない。量は上限と 1 回あたりの件数で抑え、気になる人は Off を選べる。

## 見直す条件

- sendo が、リクエストごとに、期待するユーザーかを確かめられるようになったとき。送る前の `/me` を省ける。
- 手元のデータが増え、opfs-sahpool の容量や速さで困ったとき。長く使う端末では、sendo の保管容量や記事の取り込み量に応じて手元のデータも増える。
- 先に取った全文の多くを読まずに捨てている、または、上限で足りずに開くたびに取り直していると分かったとき。先に取る記事の選び方や上限の選択肢を見直す。
- 既読にせずに読み進める使い方（一覧を動かして既読にする設定を切っているなど）で、読んでいる位置と先に取る記事がずれて困ると分かったとき。位置を一覧の表示位置から取るかを決め直す。
- 複数のタブや複数の端末で、別々の記事を開いて読む使い方で、開いている記事の本文が上限のために消えて困ると分かったとき。開いている記事を複数守るかを決め直す。
- オフラインで本文の画像が出ないことが困ると分かったとき。画像も先に取るかを決め直す。
- 先に取るリクエストが、sendo や元のサイトの負荷になると分かったとき。1 回あたりの件数や、取る時期を見直す。
- 新しい端末で、最初の同期範囲に入らない既読記事も読みたいという要望が出たとき。sendo に最初の同期を広げてもらうことを考える。
- Capacitor で包むとき。ネイティブの SQLite に替えるか、WebView の中で Wasm を使い続けるかを決める。
- タブの引き継ぎで、操作が失われたり二重になったりすると分かったとき。
