# 画像（サムネイルとフィードのアイコン）

- 状態：提案中
- 関連：[ローカルファースト](local-first.md)（ページの守り、決定の 6）、[UI とツール](ui.md)、[速さの予算](performance.md)、sendo の[画像の中継とサムネイル](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/images.md)・[差分同期](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/sync.md)

一覧のサムネイルと、フィードのアイコンを出す。画像は配信元のサイトにあるが、reader の CSP（`img-src 'self' data:`）は変えない。sendo が画像を中継し、reader からは同じオリジンの画像として読む。中継の決まり（何を中継するか、配信元に何を渡さないか、どの形式を通すか）は、sendo の決定が正で、ここには書き写さない。

ここでは、reader の側の決まり（受け取り方、キャッシュ、出し方）を決める。記事の本文の中の画像と、埋め込み（iframe）は、sendo が本文を配る段階で決める。

## 決定

### 受け取り方

1. **画像の URL は、sendo から受け取ったものをそのまま使う。** 記事の `thumbnailUrl` と、フィードの `iconUrl`（どちらも、ないときは null）。
   - reader は、この URL を組み立てない、書き換えない、中身（`url=` や `sig=`）を読まない。sendo は、あとで形を変えることがある
   - 確かめるのは、同じオリジンを指すことだけ。文字列の形（`/` で始まる、など）では決めず、ブラウザと同じ決まりで URL として解決し、解決した先のオリジンが、解決の基準にしたオリジンと同じかを見る（`/\evil.example/a` のように、形はパスでも別のオリジンに解決される値がある）。確かめるだけで、受け取った文字列は書き換えない。そうでない値は、null として扱う
   - CSP でも止まるが、同期で届くデータは外から来たものなので、重ねて守る
2. **差分同期で受けて、手元の DB に置く。** 記事とフィードの表に列を足す（マイグレーション）。
   - すでに手元にある記事は null のまま（sendo は、さかのぼってサムネイルを付けない）。最初から同期し直させない
   - フィードは、同じ ID の行がもう一度届いたら上書きする（アイコンは、あとから付く ／ 変わる ／ null に戻る）
   - 一覧を出すのに、別の問い合わせはしない（画面はネットワークを待たない）

### キャッシュ

3. **Service Worker で、画像をキャッシュする。** オフラインでも、一度出した画像を出す。
   - 相手は `GET /api/v1/images` だけ。キャッシュを先に見て、なければ取りにいく
   - 画面のファイル（アプリの外枠と wasm）のキャッシュとは、別の名前のキャッシュに入れる（`sendo-images`）。まとめて消せるようにするため
   - **入れるのは、成功（200）の応答だけ。** 401 ／ 403 ／ 502 は入れない
   - 上限は 300 件と 30 日。超えたら、最後に使ったのが古いものから捨てる。容量が足りなくなったら、このキャッシュをまとめて捨てる
4. **画像のキャッシュは、手元の DB と一緒に消す。** ログアウトしたときと、ユーザーが替わったとき（[ローカルファースト](local-first.md)の 6）。
   - 画像の応答は、その人のセッションで取ったもの（`private`）なので、次に使う人に残さない
   - セッションが切れただけ（401）のときは、手元の DB と同じく残す
   - ブラウザ自身の HTTP キャッシュに入った分は、reader からは消せない。同じオリジンの、ログインしていないと取れない画像で、ほかのサイトからは読めない（sendo が `Cross-Origin-Resource-Policy: same-origin` を付ける）

### 出し方

5. **サムネイルは、一覧の行の右に、決まった大きさの正方形で出す。**
   - 出すのは、要約も出す形（`comfortable`）のときだけ。タイトルだけの形では出さない
   - 大きさは CSS で決め、はみ出す分は切る（`object-fit: cover`）。縦横比の違う画像でも、行の高さは変わらない
   - 場所は、画像が届く前に取っておく（読み込みで一覧がずれないように）
6. **フィードのアイコンは、左のメニューと、一覧の行のフィード名の前に出す。** これまで頭文字の印を出していた場所に入れる。
7. **画像がない（null）ときと、読み込みに失敗したときは、同じ出し方にする。** 壊れた画像の印は出さない。
   - サムネイルは、場所ごと出さない
   - アイコンは、頭文字の印にする（これまでと同じ）
   - 失敗の理由（401 ／ 403 ／ 502）は区別しない。`<img>` からは分からない
8. **画像は、見えた分だけ取る**（`loading="lazy"`）。もとの大きさのまま届く（数百 KB〜数 MB のこともある）ので、画面の外の分は取らない。
9. **`alt` は空にする。** サムネイルもアイコンも飾りで、すぐ隣に記事のタイトルやフィードの名前が文字で出ている。
10. **画像を出すところは、1 つの部品にまとめる。** 遅らせて読む、失敗したら出さない、を 1 か所で持つ。あとで「回線によって出さない」などの設定を足すときに、そこだけを直せばよいようにする。

## 理由

- **sendo の中継を使い、CSP を変えない**：`img-src` を `https:` に広げると、ページに他人の JS が入ったときに、画像の URL に手元のデータを載せて外へ送れる。配信元にも、読者の IP と開いた時刻が伝わる。中継なら、どちらも起きない。
- **URL を組み立てない**：署名は sendo しか付けられない。reader が形を知らなければ、sendo は、あとで ID から引く形などに変えられる（sendo の決定の「見直す条件」）。
- **同じオリジンを指すかだけを確かめる**：中身を読まずにできる確認で、`<img src>` にほかのオリジンの URL が入るのを、CSP と二重に防げる。文字列の形で決めないのは、ブラウザが `\` を `/` と同じに扱い、タブや改行を取り除いてから解決するため。形だけを見ると、通した値が別のオリジンを指すことがある。
- **別の名前のキャッシュ**：画面のファイルのキャッシュは、アプリの版が替わるたびに入れ替わる。画像は、版と関係なく持ち続け、ログアウトでまとめて消したい。
- **200 だけを入れる**：失敗を入れると、配信元が直ったあとや、ログインし直したあとも、出ないままになる。
- **300 件と 30 日**：
  - 件数で見るのは、Service Worker のキャッシュの仕組み（Workbox）が、件数と日数でしか捨てられないため。画像 1 枚が平均 200KB だとすると、300 件で 60MB ほど（大きさは測っていない。使ってみて見直す）
  - 30 日は、sendo の `Cache-Control` と揃えた。同じ URL のまま中身が変わる画像（サイトのアイコン）が、古いまま残り続けないようにするため
  - 最後に使ったものを残すので、毎回出るフィードのアイコンは、サムネイルに押し出されにくい
- **DB と一緒に消す**：画像は、その人が購読しているフィードと読んだ記事を表す。手元の DB を消すのと同じ場面で消さないと、次に使う人のブラウザに残る。
- **サムネイルは要約も出す形だけ**：タイトルだけの形は、1 画面に多くの記事を並べて流し読みするためのもの。画像を足すと、行が高くなり、通信も増える。
- **場所を先に取る**：画像が届くたびに行の高さが変わると、読んでいる場所がずれる。スクロールで既読にする仕組みも、行の位置で判定している。
- **失敗したら出さない**：配信元が画像を消した、SVG のアイコンしかない、といった失敗は珍しくない。壊れた画像の印が並ぶより、ないほうが読みやすい。
- **`alt` を空にする**：同じ内容を読み上げで 2 回聞かせない。

## 検討した代替案

- **reader の CSP を `img-src https:` に広げる**：sendo の側の実装が要らないが、理由に書いた 2 つの穴が開く。
- **画像の決まりを `local-first.md` と `ui.md` に分けて書く**：CSP とキャッシュは前者、出し方は後者に入る。画像の決まりが 2 か所に分かれ、本文の中の画像を足すときにも両方を直すことになる。`ui.md` は、道具の選び方の決定でもある。
- **Service Worker でキャッシュせず、ブラウザの HTTP キャッシュに任せる**：作るものがないが、オフラインで出るかはブラウザ次第で、ログアウトで消せない。
- **キャッシュの上限を、容量で見る**：画像の大きさがばらつくので、件数より正確に抑えられる。ただし、入っている応答の大きさを自分で数えて捨てる仕組みが要る。まず件数で始め、足りなければ替える。
- **キャッシュを 30 日より長く持つ**（sendo は許している）：オフラインで出る画像が増えるが、中身の変わったアイコンが古いまま残る。
- **サムネイルを、タイトルだけの形でも小さく出す**：見た目の手がかりは増えるが、理由に書いたとおり見送った。
- **サムネイルを、記事の画面の先頭にも出す**：読み始めの見た目はよくなるが、もとの大きさの画像を、記事を開くたびに取ることになる。本文を配る段階で、本文の中の画像と合わせて決める。
- **失敗したサムネイルの場所を残す**（灰色の四角）：行の高さは変わらないが、画像のない記事と見分けがつかず、空の四角が並ぶ。
- **署名が合わない（403）と分かったら、最初から同期し直す**（sendo が鍵を作り直したとき）：配った URL がまとめて切れても、自分で直る。ただし、`<img>` の失敗からは 403 かどうかが分からず、Service Worker で応答を見て画面に知らせる仕組みが要る。鍵を作り直すのは、まれな、人が行う操作なので、今は作らない。

## 見直す条件

- sendo が記事の本文（HTML）を配るとき。本文の中の画像も同じ中継を通す。サニタイズ、記事の画面での出し方、キャッシュの上限を決め直す。
- 一覧の画像が重いと分かったとき（モバイルの回線での表示の速さ、通信量）。先に reader の側で和らげる（回線によって出さない、設定で切る）。それで足りなければ、sendo の決定の「見直す条件」に当たるので、sendo に知らせる。
- 画像のキャッシュが、端末の容量を使いすぎると分かったとき。上限を、容量で見る形に替える。
- sendo が署名の鍵を作り直して、配った URL がまとめて切れたとき。403 を見て最初から同期し直す仕組みを足すかを決める。
- アイコンの付かないフィードや、サムネイルの付かない記事が目立つとき。sendo の決定の「見直す条件」に当たるので、sendo に知らせる。
- sendo が、中継の URL の形や、通す形式（SVG など）を変えたとき。
