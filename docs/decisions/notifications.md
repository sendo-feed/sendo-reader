# 通知

- 状態：提案中
- 関連：[UI とツール](ui.md)（5 の PWA）、[ローカルファースト](local-first.md)（1、3、5、6 のログイン、ページの守り）、[ワークスペース](workspaces.md)（3 の範囲）、[画像](images.md)（3・4 のキャッシュ）、[コンテナ版](container.md)（3、5、8）、[記事の中の X の投稿](embeds.md)（3）、[アカウントの画面](account.md)（3 の API の窓口）、sendo の[通知](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/notifications.md)

sendo は、ベルに当たった新しい記事を Web Push で送り、通知に受信箱の未読の数も載せる。ベル、判定、通知の中身と量、登録の API は、sendo の決定が正で、ここには書き写さない。reader は、通知の許可を求めて登録を sendo に送り、Service Worker で通知を出し、押された通知の記事を開き、アプリのバッジに未読の数を出す。

## 決定

### 許可と登録

1. **通知の許可は、利用者が押したときにだけ求める。** 起動しただけ、画面を開いただけでは求めない。求めるのは、Settings の Notifications の項目と、ベルを付けたときに出す勧めの、Turn on notifications を押したとき。この端末で受ける操作は、sendo とプッシュサービスに届かないとできない（[ローカルファースト](local-first.md)の 1 の例外）。ベルを付ける操作そのものは、ネットワークを待たない。
   - 勧めは、ベルを付けたときに、この端末で受けておらず（3 の判定）、許可が拒否（`denied`）でなければ、画面の下に「この端末で通知を受けますか？」と出し、Turn on notifications と Dismiss のボタンを添える。許可がまだ決まっていなければ（`default`）押したときに許可の窓を出し、許可してあれば（`granted`）窓を出さずに登録を作る（3）。Dismiss で閉じたら、読み込み直すまで出さない（閉じた印は画面のメモリーにだけ持つ）
   - iPhone と iPad の Safari でホーム画面のアプリとして開いていない（`navigator.standalone === false` で、かつ `PushManager` がない。2 つがそろうときだけ）ときは、勧めに Turn on notifications の代わりに 2 の案内を出す。ほかの使えないブラウザー（2）では、勧めを出さない
   - 勧めは、画面の下の知らせ（[UI とツール](ui.md)の 5）と同じ場所に出す。取り消しの知らせ、記事の画面の知らせ、開いているメニューと窓より奥、新しい版の知らせより手前にする。このタブが使えないことを言う知らせ（[ローカルファースト](local-first.md)の 5）が出ている間は、勧めを出さない
   - 押す前に、`GET /api/v1/push` で使えるかと公開鍵（`publicKey`）を取り、`navigator.serviceWorker.ready` で Service Worker が動いていることを確かめておく。Settings は、開いたときに確かめ、済むまでは押せない状態で出す。勧めは、ベルを付けたときに確かめ、済んで使えると分かってから出す（済むまでは出さない）。iPhone と iPad の Safari の案内（上の項）も、`GET /api/v1/push` で使えると分かってから出し、Web Push を使えない Sendo では案内しない
   - `ready` は、取り込みが終わらない（`redundant` で終わった、dev サーバー）と返らないので、10 秒の上限を置く。超えたら、Settings には確かめられないことと Retry のボタンを出し（2）、勧めは出さない。取り込みが `redundant` で終わったと分かれば、上限を待たずに、使えないブラウザー（2）とする
   - 押したら、待ちを挟まずに `Notification.requestPermission()` を呼ぶ（3 のロックの外）。利用者の操作のすぐあとでないと、許可の窓を出さないブラウザーがある。許可してあれば（`granted`）、窓は出ずにすぐ返る。許可されたら、3 のロックを取り、`getSubscription()` を読み直してから、登録を作って送る
   - `GET /api/v1/push` の結果で分ける（[コンテナ版](container.md)の 8）。`available` が false か 404（Web Push に対応する前の Sendo）なら、Web Push を使えない Sendo とする。つながらない、時間切れ、5xx、401 と 404 以外の 4xx、3xx、形の読めない応答なら、Sendo に届かず使えるかが分からないとする。どちらでも許可を求めず、ベルを付けても勧めない。401 なら、Settings では、ほかのアカウントの画面と同じく、ログインし直すよう促す（[ローカルファースト](local-first.md)の 6）。ベルの勧めと起動したときの送り直し（3）では、何も出さない
2. **許可を求められないときと、拒まれたときは、どうすれば受けられるかを日本語で出す。** Settings の Notifications の項目に出す。
   - iPhone と iPad の Safari で、ホーム画面のアプリとして開いていない（1 と同じく、`navigator.standalone === false` で、かつ `PushManager` がない）：通知はホーム画面に追加したアプリでだけ受けられること、共有のボタンから「ホーム画面に追加」を選び、追加したアプリで開いて押すことを出す。ベルを付けたときの勧め（1）にも、この案内を出す。この見分けは、次の使えないブラウザーより先にする
   - 通知か Service Worker を使えないブラウザー（Service Worker を登録できなかった、取り込みが `redundant` で終わったときを含む）：このブラウザーでは受けられないこと
   - 拒まれた（`denied`）：reader からは求め直せない。ホーム画面のアプリなら端末の設定（iPhone と iPad では、設定アプリの「通知」で Sendo を選ぶ）で、ブラウザーならサイトの設定で通知を許可してから、もう一度押すよう出す
   - Web Push を使えない Sendo：この Sendo では通知を使えないこと。この端末で受けている（登録が残っている）なら、Turn off notifications も出す（4 の「受けない」と同じく外す）
   - Sendo に届かない、Service Worker の `ready` が上限の時間までに返らない（1）：使えるかを確かめられないことと、Retry のボタン
   - 許可の状態は、Settings を開いたときと前に出たときに読み直す。端末の設定で許可してから戻れば、押せる状態に変わる
3. **許可されたら、この端末の登録を作って sendo に送る。** `pushManager.subscribe`（`userVisibleOnly: true`、`applicationServerKey` は `publicKey`）で作り、`toJSON()` の形のまま `PUT /api/v1/push/registration` で送る（sendo の[通知](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/notifications.md)の 20）。
   - この端末で受けているかは、ブラウザーの登録（`pushManager.getSubscription()`）があり、許可が `granted` かで決める。手元の DB にも sendo にも、受けるかの印を持たない
   - 登録を作る、送り直す、外すは、タブどうしで `navigator.locks` の同じロックを取って 1 つずつにし、ロックの中で `getSubscription()` を読み直してから決める。許可を求める（`requestPermission()`）のは、ロックの外で、ロックを取る前にする（1）
   - 利用者の操作（Turn on ／ Turn off と勧めのボタン）と画面の確かめは、ロックを 10 秒（`navigator.serviceWorker.ready` と同じ上限）までに取れなければ、Retry を出す（2 の届かないときと同じ表示）。上限は取るまでだけに置き、取れたあとの処理は最後まで済ませる。上限のあとに取れたロックでは何もせずに放し、Retry と返したあとに登録を変えない。起動したときの送り直しと、ログアウトと切り替えで外すのは、待たずに呼ぶので上限を置かない
   - `subscribe` が断られたら、受けない状態のまま、受けられなかったことを出す。許可の窓を決めずに閉じた（`default` のまま返った）ら、何も出さずに押す前に戻す。どちらも、もう一度押せる
   - 送れなかったら（オフライン、sendo の失敗）、作った登録を外し、受けない状態のまま、その旨とやり直す手段を出す
   - 画面が起動したとき（タブごと）に、登録があれば、次の順で決める。ログインはページごと移るので、ログインのあとも起動になる
     - 許可が `granted` でなければ、4 の「受けない」と同じく外す。`GET /api/v1/push` の結果によらない（この場合が先に勝つ）
     - `granted` で、`GET /api/v1/push` の `available` が true なら、送り直す。`publicKey` が登録の鍵（`options.applicationServerKey`）と違えば、外して作り直してから送る。送り直しに失敗しても画面には出さず、次に起動したときにまた送る。作り直しの `subscribe` が断られたら（利用者の操作のあとではない）、先に外しているので、受けない状態になる。これも画面には出さない。Settings はそのときの登録で受けているかを出す（この項の 1 つ目）ので、次に開けば受けていないと出て、Turn on notifications で受け直せる
     - `available` が false なら、送り直さず、外しもしない（2）。Sendo に届かない（オフラインなど）か 401 なら、送り直さず、何も出さない。次に起動したときにまた確かめる
   - 送るのは core の API の窓口から（[アカウントの画面](account.md)の 3）。ほかの通信と同じく、セッションのユーザーが手元のユーザーと同じかを先に確かめ（[ローカルファースト](local-first.md)の 6）、違えば送らずに、4 のとおり登録を外す
   - 登録（エンドポイントと鍵）は sendo に送るだけにし、手元の DB、ログ、エラーの表示に入れない
   - ブラウザーが登録を消したら（許可を取り消した、プッシュサービスが消した）、受けない状態になる。自動では作り直さず、Settings かベルの勧めで入れ直す。`pushsubscriptionchange` は扱わない。ブラウザーが登録を替えたなら、次に起動したときに、替わった登録を送り直す
4. **受けないようにしたとき、ログアウトしたとき、ユーザーが替わったときは、この端末の登録を外す。**
   - 受けない（Settings の Turn off notifications）：`DELETE /api/v1/push/registration` を送り、ブラウザーの登録を外す（`unsubscribe()`）。sendo に届かなくても、ブラウザーの登録は外す。外した登録に送ると、プッシュサービスが 404 か 410 を返し、sendo が消す（sendo の[通知](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/notifications.md)の 21）
   - ログアウトとユーザーの切り替え（手元の DB を消すとき。[ローカルファースト](local-first.md)の 6）：ブラウザーの登録を外し、`unsubscribe()` が終わってから、この端末に出ている reader の通知を閉じ、覚えた `tag`（8）を消し、バッジを数え直す（11。ログアウトでは手元が空なので消え、ユーザーの切り替えでは次の人の手元の数になる）。`unsubscribe()` が投げても、通知を閉じ、`tag` を消し、バッジを数え直す。sendo の登録はセッションと一緒に消える（sendo の[通知](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/notifications.md)の 20）ので、`DELETE` は送らない
   - 外す前に届き、Service Worker が出している途中だった通知は、閉じたあとに出て、その `tag` も残ることがある。これは許す。押しても、次の人の手元にない記事なので、9 のとおり開かない。その push の `app_badge` が、数え直したあとにバッジに当たることもあるが、これも許す。次に数え直したときにそろう。iOS で、画面から取り直した通知の `close()` が通知センターから消すかは、確かめていない
   - ユーザーの切り替えは、代表のワーカーが手元の DB を消したことを、すべてのタブの画面に知らせて伝える。合図にするのは、手元にいたユーザーを別のユーザーに替えるために消したときと、ログアウトで消したとき。手元にユーザーがいないときに、来たユーザーを入れる前に消す（core の `#adopt`）のは、合図にしない。画面のユーザーが null から替わるのも、起動のたびに起きるので、合図にしない
   - この知らせは、タブどうしのやり取り（[ローカルファースト](local-first.md)の 5）の知らせの種類（`type`）を足すので、やり取りの版の番号を上げる（ローカルファーストの 5 の決まりのとおり）。版の違うタブは、版が合うまでこの知らせを受けない。代表の版が合わない間は、ログアウトも切り替えもその代表に頼めず（版が合わない失敗になる）、版の合う代表に替わってから、いつもどおり知らせを受ける。古い版のタブの画面でログアウトしたときは、古い版はこの端末の登録を外さないので、登録が残り、次の起動で次の人のセッションで送り直される。配った版は変えられないので、これは許す（前の人のセッションの登録は sendo で消えており、前の人の通知は届かない）
   - 通知の許可はブラウザーが持ち、reader からは取り消せない。次にログインした人が受けるには、Settings かベルの勧めで入れ直す（許可が残っていれば、窓は出ない）

### Service Worker

5. **Service Worker は、vite-plugin-pwa の injectManifest で自分で書く。** push、`notificationclick`、`notificationclose` を受けるため。
   - Workbox の部品は import し、1 つのファイル（`sw.js`）にまとめる。`importScripts` は使わない。Service Worker も本番の CSP の下で動き、Trusted Types を強制しているので、`importScripts` に文字列を渡せない
   - 今の動きを保つ。アプリの外枠と SQLite の wasm の precache（`/version.json` は入れない）、ないパスに返す `index.html`（sendo のパスは `sendo-paths.ts` の一覧で除く。[コンテナ版](container.md)の 3）、画像のキャッシュ（[画像](images.md)の 3・4。消したあとに遅れて届いた画像を入れない世代の印を含む）、古いキャッシュの片付け、新しい版の取り込みと切り替え（[UI とツール](ui.md)の 5。取り込んだらすぐ使い始め、開いている画面を受け持つ）
   - precache の一覧は、injectManifest が差し込む形のまま `sw.js` に入れる。workbox-build が鍵を並べた JSON にするので、`index.html` の項目は `{"revision":"…","url":"index.html"}` になる。コンテナは、この形の `index.html` の版の印を書き換える（[コンテナ版](container.md)の 5、[記事の中の X の投稿](embeds.md)の 3）。generateSW の出力の形（`{url:"index.html",revision:"…"}`）は探さない
6. **push を受けたら、届いた中身で通知を出し直す。** 中身の形は sendo の[通知](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/notifications.md)の 14。
   - 宣言型の push（`web_push: 8030`）を読むブラウザーでは `event.notification` から、読まないブラウザーでは `event.data` の JSON の `notification` から読む
   - `showNotification` に、`title`、`body`、`tag`、`data` と、`navigate` を必ず渡す。宣言型の push で出し直すときに `navigate` がないと、例外になる。`navigate` には届いた値を使わず、`tag` の記事の ID（7）から、自分のオリジンの記事の URL（`/?article=<記事の ID>`。値は `URLSearchParams` で符号化する）を組み立てて渡す。`tag` を読めなければ、reader の先頭（`/`）を渡す
   - 中身が形に合わない（`title` か `tag` が文字列でない）ときは、宣言型の push では出し直さない（宣言した通知が出る）。読まないブラウザーでは、「Sendo」とだけ書いた通知を出し、押したら reader の先頭を開く
   - 出し終えてから、`tag` を覚える（8）
   - push の中では `setAppBadge` を呼ばない。バッジは、閉じている間は push の `app_badge` でブラウザーが書き、開いている間は画面が書く（11）
   - reader を開いていても、通知は出す

### 押したとき

7. **押したことが届いたら（`notificationclick`）、その記事を開く。** 記事の ID は `tag`（`bell:<ベルの ID>:<記事の ID>`）から読む。`bell:` の次の `:` までをベルの ID、残りを記事の ID とする。読めない `tag`（`bell:` で始まらない、どちらかの ID が空）なら、reader の先頭（`/`）を開く。iOS で取り直した通知は `data` が空になる。
   - 通知を閉じ、覚えた `tag` を外してから、開いている reader の画面を、最後に前に出ていたものから選ぶ。`/oauth/authorize` と、読み込み直すと消えるものを出している画面（[UI とツール](ui.md)の 5。発行したトークンを出す Settings など、パスで分かるもの）は選ばない
   - 選んだ画面に、開く記事の ID を知らせる。画面は、読み込み直すと消えるものを出していなければ（自動の読み込み直しと同じ条件。`reloadGuard` の印を含む）、受けたことを返し、読み込み直さずに `/?article=<記事の ID>` へ移る。記事の URL を開いたとき（9）と同じ道で開く。Service Worker は、受けたことが返ったら、その画面を前に出す
   - 選べる画面がない、断られた、0.5 秒のうちに受けたことが返らないときは、`clients.openWindow('/?article=<記事の ID>')` で開く
   - 知らせには送った時刻を入れ、画面は、受けたときに 0.3 秒より古い知らせを断る。画面が断る上限は、Service Worker が待つ時間（0.5 秒）より、受けたことの返事が届く分だけ短くする。Service Worker が新しい窓で開いたあとに遅れて届いた知らせで移ると、2 か所で開く
   - Service Worker と画面の間の知らせの形は変えない。変えるときは、別の名前の知らせにする（古い版の画面は答えず、新しい窓で開く）
   - reader を終了しているときは、通知の `navigate` の URL で reader が開く（iOS で `notificationclick` が来なくても、これで開く）。記事の URL を開いたのと同じに扱う
8. **iPhone と iPad のホーム画面のアプリ（`navigator.standalone === true` で、かつ触れる画面（`navigator.maxTouchPoints > 1`））で、裏で動いているときに押された通知は、通知センターから消えた通知で見分ける。** このときは reader が前に出るだけで、`notificationclick` も `navigate` も来ない。
   - Service Worker は、通知を出し終えたら、その `tag` と覚えた時刻を IndexedDB に覚える。`notificationclose`（利用者が消した）が来たら、その `tag` を外す（`notificationclick` は 7）
   - 画面は、前に出たとき（`visibilitychange` で `visible` になったとき）に `getNotifications()` で出ている通知を取り直し、覚えた `tag` のうち出ていないものを、消えたものとして覚えから外す。取り直し始めたあとに覚えた `tag` は比べない
   - 消えたのが 1 件なら、押されたものとみなして、その記事を 7 と同じく `/?article=<記事の ID>` へ移って開く。読み込み直すと消えるものを出している画面なら、開かない。2 件以上なら、どれも開かない
   - 起動したときは、消えた `tag` を外すだけで、開かない。終了しているときに押されたなら、`navigate` で開いている
   - 新しい版への切り替えで自動で読み込み直すとき（[UI とツール](ui.md)の 5）は、読み込み直す前に `sessionStorage` に印を置く（印には何も入れない）。読み込み直したあとの起動で印を見つけたら消し、前に出ていれば、起動ではなく前に出たときと同じに扱う。裏で起動したなら、次に前に出たときに、いつもどおり扱う
   - 前に出たときに、自動で読み込み直すと決めたら、その前に出たことでは消えた通知を比べない（読み込み直したあとの、印のある起動で比べる）。読み込み直すかを先に決め（[UI とツール](ui.md)の 5）、比べるのはその結果を見てからにする
   - ほかの環境でも、消えた `tag` は起動したときと前に出たときに外すが、開かない。押したことは `notificationclick` で届く
   - 横にスワイプして消した通知と押した通知は、`notificationclose` が来ないと見分けられない。裏に回している間に 1 件だけ消してから、ホーム画面のアイコンで reader を開くと、その記事が開いて既読になる。前に出ている間に消えた通知も、次に前に出たときに消えたものに数える。この誤りは許す
9. **通知から開いた記事が、まだ手元にないときは、記事の画面のまま同期を待つ。**
   - 同期を頼み（起動したときや前に出たときの同期と重なれば、まとまる。[ローカルファースト](local-first.md)の 3）、頼んだあとに始まった同期が終わるまでは「記事を同期しています…」と出し、届いたら記事を出す。同期が終わってもなければ（受信箱から消えた、sendo に届かない）、「この記事は手元にありません。」と出す。一覧には戻さない。そう出したあとに、あとの同期で届いたら、記事を出す
   - `navigate` で開いた URL は、記事の URL を直接開いたのと見分けないので、記事の URL を開いたときはいつもこうする
   - 選んでいるワークスペースの範囲の外の記事は、記事の URL を開いたときと同じく出さない（[ワークスペース](workspaces.md)の 3）。7 と 8 で開こうとした記事なら、「通知の記事は、選んでいるワークスペースに入っていないため、開きませんでした。」と、取り消しの知らせと同じ画面の下の知らせで出す。記事の名前は出さない。7 の `openWindow` で開いた新しい窓と `navigate` で開いたときは、記事の URL を開いたのと見分けないので、この知らせは出ない

### 通知の中身

10. **通知の中身は、Service Worker が通知に出すだけにする。**
    - `title` と `body` は、届いた文字をそのまま `showNotification` に渡す。HTML として組み立てず、手も加えない（長さは sendo が切る。sendo の[通知](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/notifications.md)の 15・16）
    - 中身を、手元の DB、IndexedDB、ログ（失敗したときも）、Service Worker のキャッシュに残さない。画面にも渡さない。開く記事は ID で決め、出すのは手元の DB の記事
    - IndexedDB に覚えるのは、`tag`（ベルと記事の ID）と覚えた時刻だけ。ログアウトとユーザーの切り替えで消す（4）
    - IndexedDB のデータベースは、Service Worker と画面の両方が開く。形を変えるときに備え、どの接続も `versionchange` を受けたら閉じる

### バッジ

11. **アプリのバッジには、手元の DB のすべての未読の数を出す。** 出すのは数だけ。ワークスペースの範囲によらない（[ワークスペース](workspaces.md)の 3 の例外）。sendo の `app_badge` も受信箱の未読の合計で、同じ数え方。
    - 開いている間は、各タブの画面が手元の DB から数え、数え直すたびにその数を書く（`setAppBadge`）。0 件なら消す（`clearAppBadge`）。前に書いた数と同じでも書き、書いた数は覚えない
    - 数え直すのは、起動したとき、記事の表が変わったと知らされたとき（代表でないタブの操作も、同期で届いた分も、すべてのタブに知らされる。[ローカルファースト](local-first.md)の 5）、前に出たとき、通知を許可したとき、ログアウトとユーザーの切り替えで登録を外したとき。手元の DB を消すと記事の表も変わったと知らされるので、外す登録がない端末でも、ログアウトと切り替えで数え直す。裏にある間や閉じている間に push の `app_badge` が書いた数と、許可の前に書けなかった数を残さない
    - Badging API のないブラウザーでは何もしない。書くのに失敗したら（iOS では、通知を許可していないと書けない）、画面には出さず、次に数え直したときにまた書く
    - 閉じている間は、push の `app_badge` でブラウザーが書く。宣言型の push を読まないブラウザーでは、閉じている間はバッジが変わらない
    - この端末で通知を切っても（4）、開いている間は画面が書く。閉じている間は push が届かないので、閉じたときのバッジのまま残る。これは許す
    - ログアウトとユーザーの切り替えでも数え直す（4。ログアウトでは手元が空なので消え、切り替えでは次の人の手元の数になる）

### 守り

12. **CSP を緩めない。** プッシュサービスにつなぐのはブラウザーで、ページと Service Worker の `connect-src` は `'self'` のまま変えない。登録の API は同じオリジンの sendo にある。Service Worker は、push の中で外へ通信しない。Trusted Types で許すポリシーも足さない（[ローカルファースト](local-first.md)の「ページの守り」）。

### ベルの付け外し

13. **ベルは、ベルの組（購読と言葉。sendo の[通知](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/notifications.md)の 1〜3）ごとの操作で付け外しし、操作キューで送る。** 付けて外すのを、まとめない。
    - Search で言葉を入れたら、その言葉だけのベルを付け外しできる。言葉だけのベルは、ワークスペースの範囲によらず、すべての購読の記事に当たる（[ワークスペース](workspaces.md)の 3 の例外。範囲を絞った Search から作っても同じ）
    - manage feed では、購読のベルに言葉を足せる（購読 AND 言葉）。言葉を替えるときは、画面に出しているそのベルを外し、新しい組を付ける。sendo にベルを書き換える入口がないので、2 つの操作を外す順に積む。付けるほうが断られると（上限など）、どちらも残らない。これは許す。同じ購読のほかのベルは外さない
    - Settings の Notifications のベルの一覧は、選んでいるワークスペースの範囲の購読のベルと、言葉だけのベルを出す。範囲の外の購読のベルは、名前も数も出さず、あることだけを知らせる。外すには、その範囲に切り替える
    - 言葉は、送る前に sendo と同じ決まり（sendo の通知の 6・7）で区切って確かめ、上限を超えたら積まずに知らせる

## 理由

- **言葉だけのベルは範囲によらない**：言葉で拾うのは、どのフィードに出るか分からない話を知るためで、範囲で絞ると、その目的を外れる。通知も範囲によらず出る（6）。
- **一覧は範囲で絞る**：一覧はタブの中の画面なので、ほかの画面と同じく範囲に従う（[ワークスペース](workspaces.md)の 3）。範囲の外のベルの通知は届くので、あることだけは知らせる。
- **付け替えは 2 つの操作**：sendo に書き換えの入口がない。外す操作を先に積めば、上限ちょうどでも付け替えられる。付けるほうだけが断られるのは、ほかの端末で同時に上限に達したときなどに限られる。

- **ロックを取るまでに上限を置く**：Safari は、止めたページ（bfcache）のロックを持ったまま残すことがあり、そのあいだ、ほかのタブの Settings と勧めはずっと待つことになる。上限を処理の全体に置くと、上限のあとに取れたロックで登録を作ってしまい、Retry と返したのに受けている状態になる。取るまでだけに置き、遅れて取れたロックで何もしなければ、返した結果と登録がそろう。

- **押したときにだけ許可を求める**：起動しただけで許可の窓を出すと、何に使うか分からないまま拒まれやすい。拒まれると reader からは求め直せず、iOS では設定アプリまで行くことになる。ベルを付けたときは、通知がほしいと分かる時なので、その場で勧める。すぐ窓を出さずに勧めを挟むのは、ベルはほかの端末で受けるためにも付け、この端末では要らない人もいるため。
- **勧めたかを覚えない**：拒否を決めれば、ブラウザーがそれを覚え、勧めは出なくなる。決めずに閉じた人には、読み込み直したあとのベルでもう一度勧めるだけで、手元に印を持たずに済む。
- **許可してあっても、受けていなければ勧める**：Settings で切った人や、ログアウトとユーザーの切り替えで外れた人も、ベルを付けたその場で受け直せる。許可はもう決まっているので、窓は出ず、押せば登録を作るだけ。拒否のあとは reader から求め直せないので、勧めず、Settings に案内を出す。
- **勧めを、取り消しの知らせより奥にする**：取り消しは今押さないと消えるが、勧めは閉じるまで残る。新しい版の知らせより手前なのは、ベルを付けた操作のすぐあとに出るため。
- **受ける操作は、ネットワークを待つ**：登録はブラウザーがプッシュサービスに作り、sendo に送って初めて通知が届く。手元に反映してあとで送る形にすると、届かない登録を、受けている状態に見せることになる。ベルを付ける操作は、ほかの操作と同じく手元で済む。
- **案内を出す**：拒んだあとと、iOS でホーム画面に追加していないときは、reader の外で操作しないと直らない。どこで何をするかが分からないと、受けられないまま残る。
- **iOS の Safari を先に見分ける**：ホーム画面のアプリでない Safari には、`Notification` も `PushManager` もない。使えないブラウザーを先に見分けると、ホーム画面に追加すれば受けられる人に、受けられないと出してしまう。
- **`PushManager` がないことと合わせて見分ける**：macOS の Safari で `navigator.standalone` が何を返すかは確かめていない。タブで false が返るなら、`standalone` だけで見分けると、通知を受けられる macOS の Safari に「ホーム画面に追加」の案内を出し、受ける操作を出さない。ホーム画面に追加していない iPhone と iPad の Safari には `PushManager` がないので、両方を見れば取り違えない。
- **`GET /api/v1/push` の失敗を分ける**：404 は Web Push に対応する前の Sendo で、やり直しても変わらない。届かないときは、やり直せば使えることがある。`available` が false になったあとも登録が残っていれば、切る操作がないと、この端末の登録を外せない（[コンテナ版](container.md)の 8 の Discord と同じ）。
- **受けているかを、ブラウザーの登録で決める**：通知を届けるのはブラウザーの登録なので、受けるかの印を別に持つと、ブラウザーが登録を消したとき、手元の DB だけが消えたとき、送れなかったときに食い違う。送れなかった登録を外すのも同じ理由で、Settings では受ける状態に見えるのに届かない、を作らない。
- **登録の操作をタブどうしで 1 つずつにする**：登録はブラウザーに 1 つで、タブで分かれない。2 つのタブが同時に、起動の送り直しで作り直したり、受ける・切るを押したりすると、片方が外した登録を、もう片方が sendo に送ることがある。ロックの中で読み直せば、そのときある登録で決められる。許可を求めるのをロックの外にするのは、ほかのタブの送り直しを待つと、利用者の操作のすぐあとでなくなり、許可の窓が出ないことがあるため。
- **`ready` に時間の上限を置く**：Service Worker の取り込みが終わらないと `ready` は返らず、ボタンがずっと押せないまま残る。Retry を出せば、取り込みが済んだあとに押せる。
- **起動のたびに送り直す**：sendo は登録をセッションに結び、セッションが切れると消す（sendo の通知の 20）。送り直しは冪等で、同じ登録なら sendo は何も変えない。ブラウザーが登録を替えても、次の起動で届くので、`pushsubscriptionchange` を Service Worker で扱わずに済む。Service Worker から送ると、送る前にセッションのユーザーを確かめる道（[ローカルファースト](local-first.md)の 6）が別に要る。
- **ユーザーが替わったら、ブラウザーの登録を外す**：外さないと、次の起動で、前の人の登録を新しい人のセッションで送り直してしまう。ログアウトで外すのは、ログアウトが sendo に届かないときにも、プッシュサービスが 410 を返し、残った登録が消えるため。外し終えてから通知を閉じるのは、閉じたあとに届く push を減らすため。
- **ユーザーの切り替えを、手元を消した知らせで見分ける**：画面のユーザーは、起動のたびに、手元の DB を読むまで null で、そこから替わる。それを合図にすると、起動のたびに登録を外してしまう。手元を消すのは代表のワーカーなので、そこから知らせる。手元にユーザーがいないときの消し方も合図にすると、ログアウトのあとに次の人がログインしたとき、入れ直したばかりの登録を外してしまう。版の番号を上げるのは、上げないと、この知らせを送らない古い版の代表に、新しい版のタブの画面からログアウトや切り替えを頼めてしまうため。そのときは知らせが届かず、登録が残り、次の起動で次の人のセッションで送り直される。上げると、版の混ざる間は、版の違うタブどうしの読み書きも止まるが、読み込み直せば戻る。
- **出ている通知を閉じる**：ログアウトのあとに、前の人の記事のタイトルを通知センターに残さない。
- **injectManifest**：generateSW の Service Worker に push の処理を足すには `importScripts` が要り、Trusted Types で止まる。自分で書くと、画像のキャッシュの世代の印の名前のように、画面と Service Worker の両方が使うものを、ほかのコードと同じく import で分け合える。generateSW では、設定に文字のまま書き写すことになる。
- **通知を出し直す**：宣言型の push を読まないブラウザー（Chrome など）では、Service Worker が出すしかない。宣言型を読むブラウザーでも同じ道で出せば、書き方が 1 つで済み、出した通知の `tag` を覚えられる。試作で、裏で動いているときに押された記事を開けたのは、Service Worker が出した通知だった。出し直しに失敗しても、宣言した通知が出る（`mutable`）。
- **`navigate` を組み立てる**：届いた値をそのまま渡すと、記事の URL でない URL で reader を開きうる。`tag` の記事の ID から組み立てれば、開くのは自分のオリジンの記事の URL か先頭だけになる。
- **開いていても通知を出す**：`userVisibleOnly` の登録は、push のたびに通知を出す約束で、出さないと、ブラウザーが代わりの通知を出すか、出さない push に数えて登録を消す（iOS は 3 回で消す）。
- **push の中で `setAppBadge` を呼ばない**：iOS では、宣言型の push の中で呼ぶと promise が返らず、push が時間切れになって通知ごと出ない（試作）。
- **`tag` で見分け、IndexedDB に覚える**：iOS で通知センターから取り直した通知では `data` が空で、`tag` は残る。試作で、Cache Storage は Service Worker の書き込みが画面から見えなかったが、IndexedDB の書き込みは見えた。覚えるのを `tag` と時刻だけにすれば、手元に記事のタイトルが残らない。
- **開いている画面に記事を開かせる**：新しい窓で開くと、同じ reader の画面が増える。読み込み直すと消えるものを出している画面を移すと、発行したトークンや OAuth の許可の途中が消えるので、自動の読み込み直しと同じ条件で除く。答えを短い間だけ待つのは、押したことを受けてから少しの間しか、窓を開くことと前に出すことを許さないブラウザーがあるため。答えない画面（古い版、止まっている）があっても、新しい窓で開ける。古い知らせを画面が断るのは、待つのをやめて新しい窓で開いたあとに、遅れて受けた画面まで移らないようにするため。
- **画面が断る上限を、Service Worker が待つ時間より短くする**：同じ時間にすると、上限の間際に知らせを受けて移った画面の返事が、Service Worker が待つのをやめたあとに届き、Service Worker も新しい窓で開く。往復の分だけ短くすれば、画面が移るなら、Service Worker はその返事を待つうちに受けられる。
- **iPhone と iPad のホーム画面のアプリでだけ、消えた通知で開く**：押したことが届かないのは、そこで確かめた WebKit の不具合（bug 282935）。押したことが届く環境で消えた通知を数えると、OS が古い通知を片付けたときなどに、押していない記事を開く。試作で確かめたのは iPhone（iOS 27.2）のホーム画面のアプリだけで、iPad と macOS の Safari は確かめていない。
- **消えた通知で開く環境を、触れる画面でも絞る**：macOS の Safari の Dock のウェブアプリが `navigator.standalone` を true で返すなら、`notificationclick` が届くのに消えた通知でも開き、7 と 8 が同じ記事を 2 度開こうとする。iPhone と iPad は触れる画面なので、`navigator.maxTouchPoints` も見る。
- **1 件なら開き、2 件以上なら開かない**：記事を開くと既読になるので、取り違えると、押していない記事を既読にする。1 件だけ消えるのはたいてい押したときで、1 件だけスワイプで消してからアイコンで開くことは少ない。取り違えても、未読に戻せる。2 件以上消えるのは、まとめて消してからアイコンで開いたときが多く、どれも押していないことが多い。
- **起動したときは開かない**：終了していたなら、押した記事は `navigate` が開いている。消えた通知で開くと、アイコンで起動したときに、消しただけの通知の記事まで開く。
- **版の切り替えで読み込み直したあとは、前に出たときと同じに扱う**：新しい版を待っている画面は、裏に回ったときと前に出たときに読み込み直す（[UI とツール](ui.md)の 5）。押した通知で前に出たときに読み込み直すと、そのあとの画面は起動として扱われ、押した記事が開かない。裏に回ったときの読み込み直しも、前に出るまで終わらなければ同じになる。印を 1 つ置けば、どちらも、いつもの比べ方で決められる。読み込み直すと決めた前に出たことで比べないのは、比べ終える前に読み込み直しが始まると、消えた `tag` を外したまま記事を開かずに終わり、読み込み直したあとの起動で比べるものが残らないため。
- **出し終えてから覚え、取り直し始めたあとの `tag` は比べない**：先に覚えると、出せなかった通知を、消えた（押された）ものと取り違える。前に出たのと同じころに届いた通知も、比べると、まだ取り直しに入っていないだけで消えたように見える。
- **記事の画面で同期を待つ**：sendo は受信箱に配ってから通知を送るので、通知が届いたときには記事が sendo にあり、前に出たときの同期ですぐ届く。一覧に戻すと、押した記事を探し直すことになる。sendo から記事を直接取ると、画面がネットワークを待つことになる（[ローカルファースト](local-first.md)の 1）。
- **範囲の外の記事は開かない**：開くと、通知を押すだけでワークスペースの範囲が広がり、画面を共有している間に範囲の外の記事が出る。知らせるのは、押したのに何も起きないように見えないため。通知そのものにタイトルが出ているので、知らせても、新しく見えるものはない。
- **バッジはすべての未読で、数だけ**：バッジはアプリに 1 つで、タブごとの範囲に従えない。範囲で絞ると、範囲の違うタブがそれぞれの数を書き合う。数は、画面を共有している間もホーム画面やタスクバーで見えるが、フィードの名前も記事も出ない。通知も、sendo がベルごとに送り、タブの範囲を知らない。
- **数え直すたびに書く**：書いた数を覚えて違うときだけ書くと、覚えた数と実際のバッジが、push の `app_badge` が書いたときや書くのに失敗したときにずれ、覚えた数を捨てる時機を 1 つずつ決めることになる。開いている間にもブラウザーが `app_badge` を当てるなら、その時機にも入らず、まだ送っていない既読がある間は、次に手元の数が変わるまで sendo の数のまま残る。数え直しはもともと表の変化ごとにしていて、毎回書いても増えるのは `setAppBadge` の呼び出しだけなので、覚える数と捨てる決まりをなくし、どの場合も次に数え直したときにそろえる。前に出たときと許可したときにも数え直すのは、裏にある間に push が書いた数と、許可の前に書けなかった数を残さないため。開いている間は、まだ送っていない既読も数える手元の DB のほうが新しい。ログアウトとユーザーの切り替えでも、消さずに数え直すのは、登録を外し終えるまでの間に次の人の同期が終わると、消すことで次の人の数まで消してしまうため。
- **閉じている間は `app_badge`**：Service Worker は push の中でバッジを書けないので、sendo が数を載せ、ブラウザーに書かせる（sendo の通知の 14）。
- **切ったあとも、開いている間はバッジを書く**：通知を受けるかで書き方を分けずに済む。閉じている間に数が古いまま残るのは、宣言型の push を読まないブラウザーと同じ。
- **CSP を緩めない**：Web Push で増える通信は、ブラウザーとプッシュサービスの間と、同じオリジンの登録の API だけで、ページの通信の決まりは変わらない。

## 検討した代替案

- **起動したときに許可を求める**：受ける人は増えるが、何に使うか分からないまま拒まれ、iOS では戻しにくい。利用者の操作なしでは窓を出さないブラウザーもある。
- **ベルを押したら、すぐ許可を求める**：押す回数が 1 回減るが、この端末では受けたくない人にも窓が出て、拒むと戻しにくい。
- **勧めたことを手元に覚え、端末ごとに 1 度だけ勧める**：閉じた人には二度と出ないが、手元の印が 1 つ増え、ログアウトで消すかなどを決めることになる。
- **許可を決めたあとは勧めない**：切った人に勧め直さずに済むが、切った人やログアウトで外れた人が受け直すには、Settings まで行くことになる。
- **受けるかの印を手元の DB に持つ**：ブラウザーが登録を消したときに自動で作り直せるが、印と登録の食い違いを扱う道が増える。
- **`pushsubscriptionchange` で、替わった登録を Service Worker から送る**：替わってすぐ届くが、Service Worker がユーザーを確かめて sendo を呼ぶ道が増える。
- **ユーザーの切り替えを、画面のユーザーが替わったことで見分ける**：ワーカーからの知らせが要らないが、起動のたびに null から替わるので見分けられない。
- **知らせの種類を足すだけにし、やり取りの版の番号は上げない**：版の混ざったタブもそのまま読み書きできるが、古い版の代表の間に、新しい版の画面からログアウトや切り替えをすると、知らせが届かずに登録が残る。次の起動で次の人のセッションで送り直され、その人が Turn on notifications を押していないのに通知を受け始める。
- **generateSW のまま、push の処理を `importScripts` で足す**：今の設定を変えずに済むが、Trusted Types で止まる。
- **宣言した通知をそのまま出し、Service Worker は `tag` を覚えるだけにする**：出し直さずに済むが、宣言型を読まないブラウザーには別の道が要る。宣言したまま出た通知を `getNotifications()` で取り直せるかは、確かめていない。
- **宣言型を読まないブラウザーでだけ、push の中で `setAppBadge` を呼ぶ**：Chrome でも閉じている間にバッジが変わるが、ブラウザーで道が分かれ、見分けを誤ると iOS で通知ごと出なくなる。
- **記事の ID を `data` だけから読む**：iOS で取り直すと消える。
- **押された記事を Cache Storage に覚える**：試作で、Service Worker の書き込みが画面から見えなかった。
- **押したら、いつも新しい窓で開く**：画面に知らせる形が要らないが、開いている画面が残ったまま、同じ reader の窓が増える。
- **Service Worker と画面の間の知らせに、版の番号を付ける**：形を変えても同じ名前で送れるが、番号を比べる処理が要る。名前を替えれば、古い画面は答えず、新しい窓で開くだけで済む。
- **裏で動いているときは前に出すだけにし、記事を開かない**：取り違えはないが、iOS で通知を押しても記事が開かない。
- **2 件以上消えたら、いちばん新しい通知の記事を開く**：押したのがそれなら開けるが、違えば押していない記事を既読にする。
- **2 件以上消えたら、消えた通知の記事を並べた一覧を出す**：選び直せるが、通知のための一覧の画面と、その記事を覚える場所が要る。
- **どの環境でも、消えた通知で開く**：作りは 1 つで済むが、押したことが届く環境で、OS が片付けた通知の記事を開く。
- **版の切り替えで読み込み直す前に、消えた通知を確かめ、開く記事があれば移ってから読み込み直す**：印が要らないが、裏に回ったときに読み込み直し、前に出るまで終わらなかった画面は救えない（確かめた時点では、まだ押されていない）。
- **記事がないときは、一覧に戻す**：待たせないが、押した記事を探し直すことになる。
- **記事がないときは、sendo から記事を取って出す**：すぐ出せるが、画面がネットワークを待ち、手元の DB にない記事を出す道が増える。
- **範囲の外の記事なら、All に切り替えて開く**：押した記事が必ず出るが、画面を共有している間に、通知を押すと範囲が広がる。
- **バッジを、選んでいるワークスペースの範囲で数える**：範囲の外の数が見えないが、バッジは 1 つで、タブごとに違う範囲を持てない。
- **バッジを代表のタブのワーカーだけが書く**：書き手が 1 つで済むが、iOS でワーカーから書けるかを確かめていない。表の変化はすべてのタブに届くので、画面から書いても数はそろう。
- **最後に書いた数を覚え、違うときだけ書く**：`setAppBadge` の呼び出しが減るが、覚えた数を捨てる時機（前に出たとき、許可したとき、書くのに失敗したとき）を決めることになり、開いている間に push の `app_badge` が書いた数は、次に手元の数が変わるまで残る。
- **通知を切ったら、バッジを消して書かない**：閉じている間に古い数が残らないが、通知を受けるかでバッジの書き方が分かれる。
- **通知の中身を手元に置き、通知の一覧を出す**：あとから見返せるが、記事のタイトルが手元に残り、受信箱の一覧と役目が重なる。
- **ページと Service Worker の `connect-src` に、プッシュサービスのオリジンを足す**：Service Worker から外へ送る形にも備えられるが、プッシュサービスはブラウザーが選ぶので、足すオリジンの一覧が閉じない。今の作りでは、ページも Service Worker もプッシュサービスにつながないので、使う道もない。

## 見直す条件

- 許可してある（`granted`）ときの `pushManager.subscribe` が、利用者の操作のあと（`requestPermission()` とロックを待ったあと）でも、利用者の操作のない起動したときの作り直し（3）でも通るかは、確かめていない。通らないブラウザーがあると分かったとき。押した処理の中での呼ぶ順と、起動したときに鍵の違う登録を外してから作り直す順を決め直す（作り直しが断られると、Settings で受け直すまで受けない）。
- iOS で、裏で動いているホーム画面のアプリにも `notificationclick` か `navigate` が届くようになったとき（WebKit bug 282935）。消えた通知で見分けるのをやめる。
- スワイプで消しただけの記事が開く、という声が続いたとき。iOS が `notificationclose` を送ると分かったとき。
- iPad や macOS の Safari で、押した通知の記事が開かない、取り違える、と分かったとき（試作は iPhone だけ）。
- 宣言型の push を読むブラウザーが変わったとき、push の中で `setAppBadge` が返るようになったとき。閉じている間のバッジの書き方を決め直す。
- sendo の通知の形（`tag`、`navigate`、`app_badge`）が変わったとき。
- reader が記事を開く URL（`/?article=<記事の ID>`）を変えるとき。sendo の `navigate` と Service Worker が組み立てる URL を合わせ、通知センターに残った古い URL も開けるようにする。
- sendo がワークスペースごとに鳴らし分けるようになったとき。バッジと通知の範囲を決め直す。
