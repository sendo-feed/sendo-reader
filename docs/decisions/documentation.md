# 決定の残し方

- 状態：提案中
- 関連：[sendo の決定の残し方](https://github.com/sendo-feed/sendo/blob/main/docs/decisions/documentation.md)、[インセプションデッキ「12. 私たちの進め方」](https://github.com/sendo-feed/sendo/blob/main/docs/inception-deck.md)

sendo と同じ残し方にする。どちらかを変えるときは、もう一方も揃える。

## 決定

1. **決定はテーマごとに1ファイルにする。** `docs/decisions/<テーマ>.md` に置き、番号は振らない。一覧は [README.md](README.md) に載せる。
2. **ファイルには「今の決定」だけを書く。** 決定が変わったら、そのファイルを書き換える。古い内容や「置き換え済み」の記録は残さない。
3. **履歴は git が持つ。** 決定ファイルを変えるコミットでは、メッセージに「何を、なぜ変えたか」を書く。件名は `decision(<テーマ>): …` の形にする。
4. **経緯は git から引く。** 「なぜこうなったか」を知りたいときは、`git log -p -- docs/decisions/<テーマ>.md` を Claude に要約させる。
5. **書くのは、覆すと高くつく決定だけ。** 目安は「戻すのに数日以上かかる」か「同じ議論をまた繰り返しそう」か。それ以外は PR とコミットメッセージで足りる。
6. **決定ファイルが正。** README や AGENTS.md、sendo の技術構成（tech-deck）と食い違ったら、決定ファイルに合わせて直す（sendo の文書は sendo の PR で直す）。
7. **sendo の決定に従う。** サーバーとの約束ごと（認証、差分同期など）は sendo の `docs/decisions/` が正で、ここには書き写さない。reader の決定ファイルからは、リンクで指す。

### 言語

- 2人で開発している間は、文書、コミットメッセージ、PR、Issue を日本語で書く。識別子は最初から英語にする。
- 一般に公開するときに文書の英語版を作り、それ以降は英語版を正とする。新しいコミットメッセージや PR も英語にする。公開前の日本語のコミットはそのまま残す。

### コミットメッセージ

- Conventional Commits を土台にし、決定ファイルの変更だけ `decision(<テーマ>): …` にする。
- 規約の全文は、組織共通の [CONTRIBUTING.md](https://github.com/sendo-feed/.github/blob/main/CONTRIBUTING.md) に置く。GitHub の組織の既定ファイルはクローンに含まれず AI エージェントから見えないため、要点は `AGENTS.md` にも書く。
- `AGENTS.md` をエージェント共通の正本にし、`CLAUDE.md` は `@AGENTS.md` で読み込んで Claude Code だけの補足を足す。Codex のレビュー観点は `AGENTS.md` の「Review guidelines」節に書く。
- このリポジトリには `CONTRIBUTING.md` を置かない。置くと組織の既定が使われなくなるため。

### 決定ファイルの形

```markdown
# <テーマ>

- 状態：提案中 ／ 合意済み
- 関連：…

## 決定
## 理由
## 検討した代替案
## 見直す条件
```

1ファイルは1画面〜2画面に収める。長くなったらテーマを分ける。

### git の扱い

- `main` の履歴を書き換えない（force push しない）。履歴が決定の経緯そのものになるため。
- 決定ファイルの変更は、ほかの変更と分けて単独の PR にする。スカッシュマージでは PR が1つのコミットになるので、混ぜると決定の経緯が埋もれる。
- PR をスカッシュマージするときは、PR の説明に「何を、なぜ変えたか」を書く。その説明がそのままコミットメッセージになる。

## 理由

- **sendo と揃える。** 2つのリポジトリを同じ2人と同じエージェントが行き来するので、残し方が違うと迷う。
- **番号付きの ADR はごみになりやすい。** 決定を気軽に覆す進め方だと「置き換え済み」の ADR が積み上がり、今の状態を知るのに鎖をたどる必要が出る。
- **古い記録は AI を誤らせる。** Claude Code は `docs/` を文脈として読む。古い決定が残っていると、それを前提にコードを書いてしまう。
- **サーバーとの約束ごとは1か所に置く。** 同期や認証の決まりを reader にも書き写すと、sendo で変わったときに食い違う。

## 検討した代替案

- **sendo の documentation.md を指すだけにする**：二重に書かずに済むが、エージェントがクローンだけで決まりを読めない。
- **番号付きの ADR を積み上げる**：経緯をファイルだけで追えるが、上の理由でごみになりやすい。
- **決定を文書にしない**：一番軽いが、同じ議論を繰り返し、Claude にも方針が伝わらない。

## 見直す条件

- sendo の決定の残し方が変わったとき（こちらも揃える）。
- コントリビューターを迎えるとき。外部の人は git log をたどらないので、番号付きの ADR に移すか、決定ファイルに「主な変更」の節を足すかを決め直す。
